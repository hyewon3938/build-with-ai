# 계획서 템플릿

> `.claude/plans/<이슈번호>-<간단한설명>.md`에 저장.

```markdown
# [이슈 제목]

## 이슈
- 번호: #N
- 브랜치: <브랜치명>
- 마스터: #M (해당 시)
- design-notebook: docs/design-notebook/<master-slug>.md#phase-N (해당 시)

## 개요
[변경 목적과 배경 1~2줄]

## 변경 파일 목록
| 파일 | 변경 유형 | 설명 |
|------|----------|------|
| `src/foo.ts` | 수정 | ... |
| `docs/adr/NNNN-*.md` | 신규 | ADR 작성 (해당 시) |

## 구현 상세

### 1. [작업 단위 1]

**Before:** (기존 코드가 있는 경우)
\`\`\`typescript
// 현재 코드
\`\`\`

**After:**
\`\`\`typescript
// 변경될 코드
\`\`\`

**설명:** [왜 이렇게 변경하는지]

### 2. [작업 단위 2]
...

## ADR 작성 (해당 시)

**대상 여부**: [yes/no + 판단 근거 — references/adr-criteria.md의 5조건 기준]

**번호**: NNNN (다음 번호)

**초안**:
- Context: [배경·제약]
- Decision: [선택한 안 + 핵심 구조]
- Alternatives: [대안 A / 대안 B / ...]
- Consequences: [장점 / 단점 / 후속 작업]

## 커밋 계획
1. `feat(scope): 첫 번째 커밋 내용` - [포함 파일들]
2. `feat(scope): 두 번째 커밋 내용` - [포함 파일들]

## 테스트 계획
- [ ] [테스트 케이스 1]
- [ ] [테스트 케이스 2]

## 완료 게이트 (DoD)

> 표준 순서: `/build` 입력 → 바로 다음 줄로 `/goal` 붙여넣기 (`/goal`은 치는 즉시 그 조건으로 턴을 시작하므로 `/build`보다 먼저 치면 build 스킬 없이 구현이 시작된다). 평가자는 대화에 드러난 증거만 보므로, 조건은 명령 출력·PR 번호처럼 대화에 증거가 남는 형태로 쓴다.

- **끝 상태**: [측정 가능한 종료 조건 — 예: 구현 상세 1\~N 전부 반영, `yarn vitest run` 통과, PR 생성 + `gh pr checks` 전부 pass]
- **증명 방법**: [예: 테스트 실행 출력과 PR 체크 결과를 대화에 표시]
- **제약**: [예: 계획서 밖 파일 변경 없음]
- **턴 상한**: [예: 30턴 초과 시 중단하고 상황 보고]

## 체크리스트
- [ ] 프로젝트 컨벤션 규칙 준수
- [ ] 민감 정보 하드코딩 없음
- [ ] 타입 안전성 확인
- [ ] 에러 핸들링 포함
- [ ] ADR 작성 필요 여부 판단 완료
- [ ] design-notebook 해당 phase 섹션 갱신 (해당 시)
```
