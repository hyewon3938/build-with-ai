# ADR 작성 판단 기준

> 프로젝트에 `docs/adr/` 디렉터리가 있을 때 적용. 이번 설계가 ADR 대상인지 점검한다.

## 판단 기준

아래 조건 중 **2개 이상** 해당되면 ADR 대상:

- [ ] **되돌리기 어렵다** — 바꾸려면 여러 파일·문서·외부 시스템 동시 변경 필요
- [ ] **대안이 있었다** — 하나 이상의 대안을 놓고 고민했고, 트레이드오프 존재
- [ ] **장기 영향이 크다** — 6개월\~1년 뒤에도 이 판단을 참조할 일이 있음
- [ ] **온보딩에서 설명이 필요하다** — 새로 합류한 사람이 "왜 이렇게 짰지?" 물어볼 만함
- [ ] **판단 근거가 비자명하다** — 코드만 봐서는 왜 그렇게 짰는지 바로 안 보임

## ADR이 **아닌** 것

- 단순 기능 추가
- 버그 수정
- 코드 스타일·네이밍
- 라이브러리 버전 업 (호환성 이슈 없으면)
- 마일스톤급 출시·아키텍처 전환 → `docs/project-history.md`
- 일상 작업 → daily 로그 (gitignored)

## 작업 절차

1. 다음 번호 결정:
   ```bash
   ls docs/adr/ | grep -E '^[0-9]{4}-' | tail -1
   ```
2. 계획서의 "변경 파일 목록"에 `docs/adr/NNNN-<kebab-case-제목>.md` 포함
3. 계획서에 **"ADR 작성"** 별도 섹션 추가 (Context / Decision / Alternatives / Consequences 초안)

## ADR 포맷 (Michael Nygard)

```markdown
# NNNN. <제목>

- Status: Accepted | Proposed | Superseded by ADR-XXXX
- Date: YYYY-MM-DD
- Related: #<이슈번호>, #<관련 이슈>
- Tags: <카테고리>, <카테고리>

## Context

[배경, 제약 조건, 왜 이 판단이 필요한가]

## Decision

[선택한 안 + 핵심 구조. 코드 스니펫 OK]

## Alternatives considered

### A. <대안 이름>
- 장점: ...
- 단점: ...
- 기각 이유: ...

### B. <대안 이름>
...

### C. <본 결정> (선택)
- 장점: ...
- 단점: ...

## Consequences

### 장점
...

### 단점 / 제약
...

### 후속 작업
- [ ] ...
```

## 불변성 원칙

- `Accepted` 된 ADR 본문은 수정하지 않음 (오탈자/링크 제외)
- 판단이 바뀌면 → **새 ADR**을 만들고, 기존은 `Superseded by ADR-NNNN`으로 상태만 변경

## 판단이 애매하면

**작게라도 기록하는 쪽**을 선택. 나중에 "쓸걸" 하는 비용이 "썼는데 별 내용 아님"의 비용보다 크다.
