# /design - 기획과 대기열 스킬

요청을 인터뷰해 설계를 정하고, 설계 문서와 이슈를 만든 뒤 세션으로 나눠 대기열 파일 `LOCAL-SESSIONS.md`에 넣는다. 구현은 하지 않는다. 대기열에 넣은 세션은 `/next`나 `/build <세션>`으로 연다.

## 입력

$ARGUMENTS

## 경로 규칙

메인 체크아웃은 `git worktree list --porcelain`의 첫 `worktree` 줄이다. 대기열과 `LOCAL-CONTEXT.md` 같은 LOCAL 파일은 worktree 안에서 불렀어도 메인 체크아웃의 절대 경로로 읽고 고친다.

## 판단 기준 순서

제안이 여러 근거와 충돌하면 설계 문서의 핵심 원칙, Accepted ADR, 이슈 본문과 사용자 입력 순서로 앞의 것을 따른다. 앞의 것과 충돌하는 안은 제안하지 않고 충돌했다는 사실을 알린다. 핵심 원칙을 바꿔야 하면 그 결정을 ADR 대상으로 적는다.

## 실행 흐름

### 1. 맥락과 대기열 대조

프로젝트 CLAUDE.md, 요청과 관련된 설계 문서 절, Accepted ADR, 대기열을 읽는다. 앞선 기획이 포기한 안이나 미룬 항목이 설계 문서에 있으면 같은 안을 다시 제안하지 않는다. 이어서 요청을 대기열과 대조해 이미 있는 일인지, 일부 겹치는지, 새 일인지 정한다. 대조 방법은 `references/queue.md`에 있다. 이미 있는 일이면 그 행을 알리고 새 세부만 덧붙인 뒤 7단계로 간다.

### 2. 인터뷰

설계에 필요한 정보가 모자라면 핵심과 맥락과 의도를 묶어 한 번에 묻는다. 선택지가 뚜렷하면 AskUserQuestion으로 묻고, 옵션 라벨은 숫자나 알파벳으로 붙인다. 구조, 흐름, 데이터 모델처럼 설계의 뼈대가 되는 결정은 코드 대신 개념과 흐름으로 정리해 사용자에게 확인받는다. 세부는 맡겨 받은 범위 안에서 정한다.

### 3. 규모 판단

`references/scale-judgment.md`로 소규모인지 정한다. 소규모면 4~5단계를 건너뛰고 6단계에서 이슈 하나, 7단계에서 대기열 행 하나만 만든다.

### 4. 탐색

관련 코드, 다시 쓸 수 있는 함수, 영향받는 파일을 찾는다. 여러 디렉터리를 훑어야 하면 scout에 맡기고 결론만 받는다. 파일 하나나 사실 하나를 확인하는 일은 직접 한다.

### 5. 설계 문서

- 설계는 프로젝트 CLAUDE.md가 설계 원본으로 가리키는 문서에 적는다. 그런 문서가 없고 `docs/design-notebook/`이 있으면 그 마스터 문서에 `templates/design-notebook-section.md` 모양으로 절을 더한다. 둘 다 없으면 어디에 둘지 묻는다.
- 새 마스터 문서의 첫 절은 핵심 원칙이다. 모든 절이 이 원칙 위에서 진행된다.
- 인터뷰에서 나온 분기점, 포기한 안, 미룬 항목, 자신 없는 부분, 비자명한 제약을 `references/thought-extraction.md`대로 골라 문서에 넣는다.
- 되돌리기 비싼 결정은 전역 CLAUDE.md의 ADR 조건 5개와 `references/adr-criteria.md`로 ADR 대상인지 판단한다. 대상이면 ADR은 구현 세션이 쓰고, 이 스킬은 7단계에서 그 세션의 할 일에 ADR 작성을 적는다.
- `docs/domains/`가 있고 이번 설계가 도메인 동작을 바꾸면, 해당 도메인 문서에 새 절 제목과 ``> TODO(`/build`): 구현 후 본문 채우기`` 한 줄만 넣는다. 본문은 `/build`가 채운다.
- 커밋하는 문서는 main에 docs 커밋 하나로 올리고 푸시한다. 프로젝트 CLAUDE.md가 main 직접 푸시를 막으면 docs 브랜치로 PR을 올리고, 머지 전에 사용자 확인을 받는다. 공개 repo면 서버 주소, 개인 맥락, 운영 기록을 넣지 않고, 그런 내용은 LOCAL 파일에 적는다.

### 6. 이슈

프로젝트 CLAUDE.md가 이슈를 쓰라고 하는 repo에서만 만든다. 세션이 하나면 이슈 하나를 만든다. 세션이 여럿이면 묶음 이슈 하나와 앞 2~3세션의 이슈를 만들고, 뒤 세션의 이슈 칸에는 세션에서 만든다고 적는다. 뒤 세션 이슈는 `/build`가 그 세션을 열 때 만든다. 이슈 본문은 공개 텍스트라 전역 보안 규칙을 따르고, 제목은 프로젝트 커밋 컨벤션 형식으로 쓴다.

### 7. 세션 나누기와 대기열 반영

`references/queue.md`대로 세션을 나누고, 새 행의 순서를 정하고, 행의 칸을 채운다. 대기열 파일이 없으면 같은 문서의 파일 모양으로 새로 만든다. 우선순위가 갈릴 때만 사용자에게 묻고, 순서나 내용이 바뀐 기존 행은 바꾸기 전과 후를 함께 보여 준다.

### 8. 반박 검증

직접 확인하지 않은 실태·수치 주장과 되돌리기 비싼 결정에만 verifier를 붙인다. 주장 하나에 verifier 하나씩 병렬로 띄우고, 반박을 통과한 것만 설계 문서와 대기열에 남긴다. 작은 기획은 0~1개로 충분하다.

### 9. 완료 보고

첫 줄에 결과를 쓰고, 그 뒤에 설계 문서와 커밋, 이슈 링크, 대기열에 넣거나 바꾼 행, ADR 대상, 사용자가 정할 남은 선택을 적는다. 마지막 줄에는 다음 세션을 새 세션에서 `/next`나 `/build <세션>`으로 연다고 적고, 첫 세션의 여는 날짜를 함께 적는다.

## 주의사항

- 이 스킬은 코드를 고치지 않는다. 소규모라도 구현은 `/build`가 한다.
- 비공개로 남길 회고나 실수는 `docs/_personal/design-drafts/`가 있는 프로젝트에서만 그곳에 적는다.
- 새 세션에 넘길 때는 대기열 행 이름과 이슈 번호만 전달한다. 설계 문서나 스킬 본문을 프롬프트에 복사하지 않는다.
