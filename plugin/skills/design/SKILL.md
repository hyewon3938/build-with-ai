# /design - 기능 설계 스킬

사용자 요청을 인터뷰하고, 의사결정 흐름을 보존하면서, `/build`가 바로 구현할 수 있는 계획서를 작성한다.

## 입력

$ARGUMENTS

## 핵심 원칙 — 사고가 휘발되지 않도록 문서에 분산

### 5-doc 아키텍처 (공개)

| 문서 | 역할 | 수명 | owner |
|------|------|------|-------|
| `.claude/plans/<이슈>-*.md` | 구현 직전 메모 | 휘발 (머지 후 `/build`가 `_archive/`로 이동) | `/design` |
| `docs/design-notebook/<master>.md` | 마스터 단위 서사 (Phase 별 섹션 누적) | 영구, 진화 | `/design` + `/build` |
| `docs/adr/NNNN-*.md` | 되돌리기 어려운 결정 | 영구, 불변 | `/design` |
| `docs/features.md` | 현재 기능 카탈로그 | 현황 | `/build` |
| `docs/domains/<domain>.md` | 도메인 상세 (스키마·API·로직) | 영구, 진화 | `/design`(phase 섹션 골격) + `/build`(본문 채우기) |

> **프로젝트에 `docs/domains/` 디렉토리가 없으면 도메인 문서 단계는 건너뛴다.**

### 비공개 보조 문서 (gitignored)

| 문서 | 역할 |
|------|------|
| `docs/_personal/design-drafts/<이슈>-*.md` | 비공개 회고 (감정·실수·솔직 분석) — iCloud 백업 symlink |
| `docs/_personal/portfolio-candidates.md` | 포폴 어필 누적본 — 이력서·면접·README 1순위 참조점 |

### 소스 우선순위 (옵션 제안·판단 시)

옵션이나 판단이 여러 소스와 충돌할 때:

1. **마스터 단위 핵심 원칙** (design-notebook 첫 섹션 또는 MEMORY `project_*_core_principles.md`) — 변경 불가, 변경 시 ADR
2. **ADR (Accepted)** — 마스터 또는 도메인의 결정 판례
3. **이슈 본문 / 사용자 입력** — 가장 구체적이지만 우선순위 가장 낮음

→ 충돌 발견 시 옵션 제안 보류 + 사용자에게 명시 보고. 핵심 원칙이 바뀌어야 한다면 ADR 작성부터.

### 메타 repo 인지

이 프로젝트는 **`github.com/hyewon3938/build-with-ai`** 메타 repo와 연결되어 있다 (`reference_build_with_ai_repo.md`). AI 협업 방식 자체에 대한 어필·정리는 그쪽으로 이관 가능 — 본 프로젝트의 portfolio-candidates는 본 프로젝트 컨텍스트가 명시되는 표현만 누적한다.

## 실행 흐름

### 1. 요청 분석

요청 파악. 마스터 이슈의 phase 진입인지, 독립 작업인지 확인.

### 2. 마스터 컨텍스트 cross-check (phase 진입 시 필수)

마스터 이슈(여러 phase로 나뉘는 단위) 작업이면 옵션 제안·인터뷰 시작 **전에** 반드시 cross-check:

- [ ] 마스터 ADR (Accepted) — 모두 읽었나? 이전 phase가 채택했거나 기각한 안과 충돌 안 하나?
- [ ] design-notebook **핵심 원칙 섹션** — 마스터 단위 헌장 (변하지 않는 원칙) 읽었나?
- [ ] MEMORY `project_<master>_core_principles.md` — 핵심 원칙 메모리 있나?
- [ ] 이전 phase의 "포기한 안" 섹션 — 재제안하지 않게 확인했나?
- [ ] 직전 phase의 마무리 기록 — `project-history.md`·`features.md` 반영이 누락됐으면 이번 계획서에 보충 항목으로 포함했나? (스킬 밖에서 close된 작업의 기록 누락을 다음 진입 시점에 회수)

cross-check 결과를 사용자에게 한 줄 재확인 (예: "v2 핵심 원칙: LLM 텍스트 의존 최소화 + outcome 검증. 이 위에서 진행해도 되지?"). **이 단계 생략하면 옵션 제안 단계에서 핵심 원칙과 충돌하는 안을 무의식적으로 제안할 위험이 높다** (2026-05-16 #390 인터뷰에서 실제 발생).

### 3. 인터뷰

설계에 필요한 정보가 부족하면 질문. 핵심·맥락·의도를 묶어서 **한 번에** 묻고, 매 단계 재확인하지 않는다. 선택지가 뚜렷하면 AskUserQuestion 활용 — 옵션 라벨은 아라비아 숫자(1, 2, 3) 또는 알파벳(a, b, c)만 (그리스 문자 금지).

옵션 제안 시 **매번 소스 우선순위 적용** — 제안이 핵심 원칙·ADR·이전 결정과 충돌하면 보류 + 보고.

**핵심 결정 체크포인트**: 설계의 뼈대가 되는 결정(구조·흐름·데이터 모델)은 코드가 아니라 개념·흐름 수준으로 정리해 명시적 체크포인트로 확인받는다. 디테일은 위임받고, 핵심은 사용자가 직접 검증할 수 있게.

### 4. 규모 판단

소규모(파일 1\~2개) → 이슈/브랜치 없이 직접 처리 후 커밋. 중규모 이상(파일 3개+, 새 기능, 구조 변경) → 아래 전체 흐름.

세부 기준: `references/scale-judgment.md` 참조.

### 5. GitHub 이슈 + 브랜치 (중규모 이상)

```bash
gh issue create --title "<커밋 컨벤션 형식 제목>" --body "<설명>" --label "<라벨>"
git checkout -b <type>/<이슈번호>-<간단한설명>
```

라벨/브랜치 네이밍은 프로젝트 컨벤션 따름. **이슈 본문·브랜치명은 공개 텍스트** — 보안 규칙 준수 (민감 정보·개인 상황 노출 금지, 포트폴리오용 문서로 취급).

### 6. 코드베이스 탐색

관련 기존 코드, 재사용 가능 함수, 영향 받는 파일 파악. `docs/conventions.md` + 기존 ADR(`docs/adr/`) 확인.

여러 파일·디렉터리를 훑어야 하는 탐색은 scout 서브에이전트에 병렬 위임하고 **결론만** 받는다 — 메인 컨텍스트는 설계 판단용으로 보호. 단일 파일·단일 사실 확인은 직접.

### 7. ADR 작성 여부 판단

조건 2개 이상이면 ADR 대상. 기준 + 포맷: `references/adr-criteria.md` 참조.

### 8. design-notebook 갱신 여부 판단

마스터 이슈 작업이거나 새 phase 시작이면:
- `docs/design-notebook/<master-slug>.md` 존재 확인
- 없으면 신규 작성 — **첫 섹션은 반드시 "## 핵심 원칙"** (변하지 않는 헌장, 모든 phase가 이 위에서 진행)
- 있으면 새 Phase 섹션 추가
- 섹션 템플릿: `templates/design-notebook-section.md` 참조

### 8-2. 도메인 문서 phase 섹션 골격 작성 (해당 시)

프로젝트에 `docs/domains/<domain>.md`가 있고 이번 phase가 그 도메인 기능에 영향을 주면 **반드시 phase 섹션 골격을 미리 작성**한다 (구현 전):

1. 영향 도메인 식별 — 계획서의 변경 파일 목록 기준 (예: `src/agents/insight/*` → `docs/domains/insight.md`)
2. 도메인 문서를 열고 마지막 섹션 번호 확인 → 새 번호로 phase 섹션 헤더 추가
3. 골격(TODO 마커)만 작성, 본문은 `/build` 단계에서 채움:
   ```markdown
   ### N. <마스터명> — Phase X (<phase 제목>)

   > TODO(`/build`): 구현 후 본문 채우기. 데이터 모델 / 트리거 / 흐름 / 명령어 / 크론 시각 / 회고 등 phase 산출물 요약
   ```
4. **누락하면 `/build` 단계에서 누락이 발견됨** — phase 섹션 골격이 없으면 `/build`가 빈 도메인 문서에 임시 추가하는 임기응변 발생. 미리 작성하는 게 핵심.
5. 계획서 "구현 상세" 마지막에 "**도메인 문서 본문 채우기**" 항목을 명시적으로 포함 (체크박스).

> 예외: 도메인 문서 자체를 신설하는 phase거나 phase가 도메인 로직 변경 없는 인프라/리팩토링 작업이면 건너뛸 수 있음 — 단 사용자에게 한 줄 보고.

### 9. 구현 계획서 작성

`.claude/plans/<이슈번호>-<간단한설명>.md` 저장. 템플릿: `templates/plan-template.md` 참조.

계획서에는 **완료 게이트 (DoD)** 섹션을 반드시 포함한다 — `/build` 세션이 `/goal`로 걸 수 있는, 대화에 증거가 남는 형태의 검증 가능한 종료 조건 (측정 가능한 끝 상태 + 증명 방법 + 지키면서 갈 제약 + 턴 상한).

### 10. 인터뷰 사고 추출

설계 중 발생한 의사결정 분기점·포기한 안·회고·미룬 항목을 자동 식별 (고정 개수 X, 기준 기반). 식별 기준: `references/thought-extraction.md` 참조.

식별된 항목 분류:
- 공개 가능 → design-notebook 해당 phase 섹션에 통합
- 비공개 → 단계 12로

### 11. 포폴 어필 후보 제안 (phase 마무리, 새 항목)

이번 phase에서 어필 가능한 항목 1\~3개 자동 제안. 카테고리:
- **프로젝트 어필**: 기술 결정·아키텍처 차별점 (이번 phase의 ADR Alternatives에서 발굴)
- **작업 방식 어필**: AI 협업·문서 체계·설계 흐름의 비자명한 패턴

각 후보에 한 줄 정의 + 원천 link 제안. 사용자가 선택 → `docs/_personal/portfolio-candidates.md`에 append.

#### 11-1. 추천 평가 동봉 (필수)

후보를 나열만 하지 말고 **각 후보에 추천/비추천 + 근거를 같이 제시**한다. 사용자가 매번 4개 옵션을 처음 보는 사람처럼 비교 검토하지 않아도 되게.

**추천 판단 기준** (다음 중 2개 이상이면 추천):
- **일반화 가치**: 본 마스터 외에도 적용 가능한 패턴 — "다른 프로젝트/도메인에서도 답으로 들 만한가"
- **비자명성**: 코드만 봐서는 안 보이는 결정·과정 — "면접에서 들었을 때 '오, 그렇네'가 나오는가"
- **원천 안정성**: ADR/design-notebook 등 link 가능한 원천이 명확 — "근거를 묻을 자료가 영구 문서로 남는가"
- **단발 vs 누적**: 한 사례가 아니라 phase 마무리에서 한 번 더 부상한 패턴 — "이전에도 비슷한 게 있었나"

**제시 형식**:
```
**추천 (N개)**
1. <후보 이름> — <왜 추천: 위 기준 중 무엇이 강한지>
...

**비추천 (M개)**
2. <후보 이름> — <왜 비추천: 부분집합·단발성·원천 모호 등>
```

#### 11-2. "추천할 만한 게 없으면 없다고 말한다"

phase 산출물에서 진짜 어필 후보가 안 보이면 **억지로 만들지 않고** 사용자에게 "이번 phase는 portfolio 어필 후보 없음 (사유: ...)" 보고. 가짜 후보 누적은 portfolio-candidates 신호를 죽인다.

> design-notebook(공개)에는 "## 기술적 의의" 1\~2줄 중립 표현만, 자세한 어필 표현·면접 답변 초안은 portfolio-candidates(비공개)에 누적 (C안 분리).

### 12. design-drafts 트리거 (구현 전 마지막 질문)

사용자에게 명시적으로 묻는다:

> "솔직 회고나 비공개로 남길 거 있어? (감정, 실수, 비공개 의도, 자신 없는 부분 등)"

있으면 `docs/_personal/design-drafts/<이슈번호>-<설명>.md`에 저장.

### 13. 사용자 확인

계획서 요약 + 갱신된 design-notebook 섹션 요약 + 추가된 portfolio-candidates 항목 보여주고 확인. 수정 요청 반영.

### 14. 완료 안내

```
설계 완료!

계획서: .claude/plans/<파일명>.md
design-notebook: docs/design-notebook/<master>.md (갱신)
ADR: docs/adr/NNNN-*.md (해당 시)
도메인 문서 phase 섹션 골격: docs/domains/<domain>.md (해당 시)
portfolio-candidates: docs/_personal/portfolio-candidates.md (해당 시)
이슈: #N
브랜치: <브랜치명>

다음 단계 — 아래 세 줄을 위에서부터 순서대로 입력하면 끝 (그대로 복사):

/compact 구현 계획서(<계획서 경로>)와 변경 파일 목록 중심으로 요약. 코드 탐색 과정은 버려도 됨
/build
/goal <완료 게이트를 한 줄로 압축해 여기 제공>

① 요약이 끝나면 ② /build ③ /goal을 연달아 입력한다. /build가 구현을 시작하고,
/goal은 그 위에 완주 게이트를 건다 — 구현 턴이 도는 중에 쳐두면 턴이 끝난 뒤 적용된다.
이후는 자동: 매 턴 끝마다 평가자가 게이트 충족을 판정하고, 미충족이면 알아서 재개한다.
③을 놓쳤다면: build가 멈춰서 "이어서 해줘"를 치고 싶어지는 첫 순간에 /goal 줄을 대신 친다.
```

> **순서 근거**: `/goal`은 게이트를 걸어두기만 하는 명령이 아니다 — 치는 즉시 그 조건을 지시문 삼아 턴이 시작된다. `/build`보다 먼저 치면 build 스킬 절차(게이트 확인·문서 갱신·리뷰·PR·CI 확인) 없이 구현이 시작돼 버린다. 작업 시작은 항상 `/build`, `/goal`은 그 위에 얹는 완주 게이트다. `/build` 뒤에 걸면 게이트가 여는 턴은 같은 세션의 연속이라 build 스킬 맥락 위에서 이어진다 (세션 중간 설정은 정식 지원). 완료 안내는 반드시 위 형식대로 **복사 가능한 세 줄**을 실제 값으로 채워 출력한다 — 순서를 산문으로 풀어 쓰지 않는다.

> 새 세션으로 인계할 땐 휘발 컨텍스트(계획서 경로, 이슈/PR 번호, 머지 상태)만 전달 — 헌장·ADR·스킬 본문을 프롬프트에 복제하지 않는다 (복제본 drift 사고 방지).

## 주의사항

- 이 스킬은 세션 모델을 그대로 사용한다 (모델 고정 핀 제거, 2026-07-12) — 판단이 무거운 설계는 상위 모델 세션에서 여는 걸 권장
- 설계 단계에서는 코드를 직접 작성하지 않는다 (소규모 제외)
- 계획서는 추가 질문 없이 구현 가능한 수준
