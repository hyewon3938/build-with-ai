# writing — AI 말투·번역투 필터

> 2026-06~08 README·설계 문서·각종 제출 폼 작업에서 사용자가 준 문체 피드백을 전수 수집해 패턴화한 것.
> 대상: 사람이 읽는 한국어 산문 전부 — 채팅 답변, 설계 문서, HTML·도식에 넣는 문구와 카드 제목까지 포함. 코드 주석은 대상 아님. 화면용 짧은 라벨이라고 예외가 되지 않는다 (2026-08-25 설계 허브 카드 문구에서 위반이 반복돼 명시).
> 사용법: 지원서·이력서·README·공개 설계 문서·이슈·PR 본문처럼 밖에 내보내는 글은 쓰기 전에 references 폴더의 파일 3개를 모두 읽는다. 채팅 답변, 화면 문구, 내부 문서는 이 파일만 보고 쓰고, §5 셀프 체크에서 걸린 항목이나 판단이 애매한 항목만 해당 references 절의 교정례를 읽고 고친다. 어느 쪽이든 쓰기 전에 §1~3을 머리에 놓고, 쓴 뒤 §5를 돌린 다음 보여준다.

## 0. 기본 톤

담백 · 존댓말(지원서·이력서) · show-don't-tell · 두괄식. 형용사로 주장하지 않고 사실과 구조로 보여준다.
**멋있는 문장을 만들려는 순간이 가장 위험하다.** 실제 거절 사유 1위가 "너무 과해", "너무 문학적", "AI스러워"였다. 잘 쓴 문장이 아니라 사람이 말하듯 흐르는 문장이 목표다.

## 1. 문장 구조 — 금지 패턴 (전부 실제 지적 사례)

### 1-1. 짧은 단정 꼬리문장 · 여운 마무리
"~가 아니다." 식으로 짧게 끊어 강조하거나 짧은 문장으로 멋지게 마무리하는 영어식 punch line. 앞 문장에 이어 붙이거나 보통 길이의 서술로 끝낸다.
- ✕ 지금도 매일 돌아갑니다. → ○ 현재까지 매일 사용 중인 시스템입니다.

### 1-2. 짝대기(—)·콜론 뒤 임팩트 문장, 편집자적 부제
쉼표로 잇거나 문장으로 풀고, 부제와 괄호 라벨 장식은 달지 않는다.
- ✕ 기준은 하나다 — 유저가 이 존재의 메시지를 기다리게 되는가.

### 1-3. 선나열-후회수 화법 (대표적 번역투)
앞에 요소를 줄줄 나열해 놓고 마지막에 한 번에 받는 구조.
- ✕ 답장이 빨라지고 느려지는 것도, 먼저 건네는 말도 모두 그 삶에서 나옵니다. → ○ 캐릭터는 자기 삶을 기반으로 답장 텀과 대화 소재가 정해집니다.

### 1-4. 재료 문장 이어붙이기
이력서 불릿·JD 문장·이전 버전 문서를 그대로 이어 붙이면 바로 티가 난다. 문장마다 판단(왜·그래서)을 담아 앞 문장을 받아 잇고, JD 문구는 같은 자리에 같은 단어를 쓰되 문장 자체는 복사하지 않는다.
- 조사 하나로도 잇는다: "고도화하는 과정을 반복해왔습니다" → "고도화하는 과정도 반복해왔습니다".

### 1-5. 부정 후 긍정 ("~가 아니라 ~다")
부정 대신 비교로 순화한다.
- ✕ 한 번에 큰 감정을 주는 게 아니라, 일상에 스며들 때 애착이 생긴다. → ○ 한 번에 큰 감정을 주는 것보다는 일상에 계속 함께할 때 애착이 생긴다.

### 1-6. 어중간한 종결
명사형·나열형으로 끝내지 않는다("케이스로." → "케이스로 처리."). 이유 설명(~하기 때문이다)보다 결과 통보(~하도록 구성했습니다)가 기본형이고, 시스템을 주어로 한 순수 현재형 종결만 이어지면 번역투로 읽혀서 만든 사람이 드러나는 종결(~하도록 해뒀습니다)을 주로 쓴다.

### 1-7. 문장형 타이틀 · 압축 조어 라벨
타이틀·라벨·범례·표 머리글은 짧은 명사구로 쓰고, 읽기 전에 내용이 예측돼야 한다. 문장형, 압축 조어, 자기 홍보 라벨, `~다` 종결, 수동태, 의문형, `~하면` 조건절 종결, 설명 문장을 `~것`으로 접은 제목을 모두 쓰지 않는다. 툴팁·본문처럼 여러 문장이 이어지는 산문은 평서형 그대로 둔다.
- ✕ 왜 값으로 바꾸나 → ○ 값으로 바꾸는 이유

### 1-8. 괄호 보충 설명
괄호 속 보충 설명은 문장에 녹인다.
- ✕ (이벤트와 컨디션이 인과로 엮여 있다) → ○ 각 이벤트는 서로 인과 관계를 형성하며, 회식이 있던 다음 날엔 피곤해하는 식으로 나타납니다.

### 1-9. 결론 먼저 짧게 던지고 뒤에서 설명하기 (영어 문단 구조)
결론을 한 문장으로 세우고 다음 문장에서 근거를 붙이면 번역투로 읽혀서, 이유와 결론을 한 문장에 묶는다. §1-1과 한 쌍으로, 짧은 문장이 혼자 서 있으면 문단 앞뒤 어느 쪽이든 의심한다.
- ✕ 답장 텀도 일정마다 지정하지 않고 두 태그 조합으로만 정했습니다. 일정이 늘수록 하나하나 관리하기 어려워지기 때문입니다. → ○ 답장 텀은 일정마다 지정하면 종류가 늘수록 관리하기 어려워져서, 두 태그의 조합으로만 정했습니다.

### 1-10. 감정·상태 명사를 주어 자리에 앉히기
마음·느낌·감각 같은 추상 명사가 사람이 하는 일의 주어 자리에 앉으면 번역투로 읽혀서, 사람을 주어로 되돌린다.
- ✕ 연결이 그리운 마음은 남습니다. → ○ 사람과 이어지는 건 여전히 그리워합니다.

### 1-11. 정의 문장에 예시를 끼워 붙이고 부연으로 마무리하기
정의는 정의만 담아 쓰고, 예시가 필요하면 표나 뒤 문단의 제자리에 둔다. 마지막 문장이 앞 내용을 다른 말로 한 번 더 설명하면 지운다.

### 1-12. 부정을 앞세워 긍정을 강조하기
`~하지 않아서 ~합니다`, `~하지 않고 ~합니다`처럼 하지 않는 일을 앞에 세우면 전하려는 긍정이 뒤로 밀린다. 하는 일을 먼저 쓰고, 하지 않는 일은 꼭 필요할 때만 뒤에 덧붙인다. 하지 않는 일 자체가 전하려는 내용인 문장과 조건절은 대상이 아니다.
- ✕ 당분간 다시 고백하지 않고, 하던 플러팅을 더 적극적으로 합니다. → ○ 하던 플러팅을 더 적극적으로 하고, 다시 고백하는 것은 당분간 미룹니다.

규칙별 전체 교정례와 지적 경위는 `references/sentence.md`에 있다.

## 2. 어휘 — 피하는 단어

### 2-1. 의인화·추상·문학적 표현
사물·개념이 살아 움직이는 표현은 실무적이고 직관적인 동사로 바꾼다. 깔다·새다 같은 공간 비유와 층·축·구멍·배선 같은 명사도 같은 부류라 시스템 동작 설명에 쓰지 않는다(§2-8).
- ✕ 한 달치가 깔린다 → ○ 한 달치를 미리 만들어 둔다

### 2-2. 일상에서 안 쓰는 단어·독자가 모를 용어
품이 든다·짚다·견주다·간주하다·클램프처럼 일상에서 안 쓰는 말과 독자가 모를 용어는 풀어 쓰거나 뺀다. 초등학생이 처음 읽어도 맥락이 잡혀야 한다. 다만 사람들이 이미 그 말로 쓰는 용어와 외래어는 그대로 둔다(§2-7). 수량은 2~3개, 3~4명처럼 숫자로 쓰고 두셋·서넛·두세·두어로 풀지 않는다.
- ✕ 원시 로그 → ○ 기록

### 2-3. 구어체 침투
편한 구어와 "거기서" 같은 지시어는 담백한 문어로 바꾼다. 판단을 `~라고 봤습니다`처럼 `보다`로 받으면 판단한 사람이 흐려져서 `~라고 생각했습니다`로 쓴다.
- ✕ 한 달치를 미리 깔아 → ○ 한 달치를 미리 정해두고

### 2-4. 가상 대사·따옴표 강조
작은따옴표 가상 대사와 쌍따옴표 키워드 띄우기는 AI스럽게 읽혀서, 예시 문장이 필요하면 따옴표 없이 서술로 쓴다. 기능 문서에서 캐릭터처럼 제품이 내보내는 말을 인용할 때만 작은따옴표로 감싼다.
- ✕ '요즘 너무 늦게 자더라' 한마디로 방향을 잡는데

### 2-5. 데이터·시각·시스템을 동사의 주어로 세우는 의인화
데이터나 시각이 사람처럼 행동하는 문장은 주어를 사람·코드·밤 정리 같은 실제 행위자로 되돌리고 목적어를 생략하지 않는다. '경계' '실제' 같은 압축 명사는 처음 나올 때 무엇인지 한 문장으로 소개한 뒤 쓴다.
- ✕ 태그가 잡은 것을 판정 없이 쌓는다 → ○ 모델이 답장에 표시를 붙이면 코드가 그 문장을 그대로 적어 둔다

### 2-6. 뜻을 뭉갠 동사·명사
짧게 만들려다 뜻이 뭉개진 말은 읽는 사람이 무슨 일인지 그릴 수 없어서, 정확한 표현이 길면 긴 쪽을 쓴다. 이름은 핵심으로 붙이고, 이름만 보고 무엇을 하는지 그릴 수 있게 짓는다.
- ✕ 일정을 접는다 → ○ 취소한다 / 미룬다

### 2-7. 과잉 번역 — 이미 쓰는 말 억지로 바꾸기
키·스키마·플러팅·컨디션처럼 사람들이 이미 그 말로 부르는 기술 용어와 외래어는 그대로 쓴다. 바꾼 말을 소리 내 읽었을 때 그 자리에서 그렇게 쓸 사람이 없으면 원래 말이 맞다. 더 많이 쓰이는 한국어 짝이 있으면 한국어를 쓰고, 독자가 모르는 외래어는 풀어 쓰거나 한 번 소개한다(§2-2).
- ✕ 중복 열쇠 제거 → ○ 중복 키 제거

### 2-8. 구조를 공간·물건 이름으로 부르기
분류·설정·문서 구조는 몇 가지인지, 어디에 적었는지, 무엇이 안 되는지 그대로 세고, 층·축·구멍·배선 같은 공간·물건 이름으로 부르지 않는다. 말·대화·관계의 진행도 흘리다·열다·닫다·오르다 같은 물리 동작이나 `~가 나오는 자리` 같은 위치로 쓰지 않는다. 눈에 보이는 실제 공간·물건을 가리킬 때는 그대로 쓴다.
- ✕ 규칙을 두 층으로 가르기 → ○ 규칙을 두 가지로 나누기

규칙별 전체 교정례와 지적 경위는 `references/vocabulary.md`에 있다.

## 3. 구성 — 흐름

- **두괄식.** 핵심 먼저, 근거·예시는 뒤. 문장 앞의 꾸미는 말을 길게 늘어놓지 않는다.
- **낯선 개념은 등장 전에 소개.** 독자가 아직 모르는 단어(블록·교체·가설 등)를 설명 없이 쓰지 않는다.
- **억지 연결 금지.** 동기 → 사실 → 연결 순서로 자연스럽게 겹치게 한다.
- **같은 단어 반복·가짜 연결 금지.** 이웃 문장에 같은 단어가 연달아 나오면 지시어로 받거나 문장을 합치고, `~하고/~해서`로 이을 때는 실제 인과·근거 관계인지 확인한다.
- **전제와 뒤 내용의 아귀 맞추기.** 앞에서 세운 전제가 바로 뒤 내용과 맞물려야 한다.
- **구구절절 금지.** 조건·부연을 다 담으려는 긴 문장은 나누거나 버린다. 이해를 돕지 못하는 예시는 노이즈다.
- **당연한 내용 삭제.** 설명할 가치가 없는 당연한 설계는 뺀다.
- **개발일지 화법 금지.** 다 만들어진 상태를 기준으로 결과만 서술하고, 개선 전후 비교는 본문에서 빼서 따로 한곳에 모아 둔다.
- **내부 작업 용어와 진행 상태를 문서에 쓰지 않는다.** 이관·개편·정식본·현 구현·새 구조 같은 말은 우리 작업 일정을 아는 사람만 읽을 수 있다. 예시 자리에는 값만 쓴다.
- **한 줄 설명은 핵심을 앞에 둔다.** 아직 소개하지 않은 고유 이름을 앞자리에 놓으면 그 이름부터 걸린다.
  - ✕ 밤 정리가 다시 써서 하루 동안 같음 → ○ 하루 동안 고정 · 매일 새벽에 그날 내용으로 갱신
- **날짜와 시각 표기.** 날짜는 7/3, 시각은 19:40으로 쓴다.
- **자기 작업 ↔ 회사 직접 동급 비교 금지.** "제가 해온 작업과 결이 비슷하다고 느꼈습니다"처럼 내 경험을 주어로 쓴다.
- **동작 설명은 장면이 그려지게, 마무리는 설계 귀결로.** 제품 동작은 독자가 그림을 그릴 수 있는 구체 행동으로 쓰고, 마지막 문장에 그 결과가 나오도록 설계했다는 인과(~해 두기 때문에 ~한다)까지 담는다.
- **핵심 주장을 관형절 속에 묻지 않는다.** 주장을 본동사로 먼저 말하고 대응을 잇는다.
- **같은 구조의 문장을 연달아 쓰지 않는다.** 같은 틀이 두 문장 연속되면 하나를 뒤집어 변주한다.
- **한계 서술은 결핍 나열이 아니라 인지+우선순위로.** 지금 집중하는 것을 앞에 세우고 한계마다 계획으로 마무리해서, 솔직하되 방치로 읽히지 않게 한다.

항목별 교정례와 지적 경위는 `references/composition.md`에 있다.

## 4. 프로세스 규칙

1. **원본 소스에서 새로 뽑는다.** 프로젝트 README → 이력서 → 지원서·프로필 순서로 원본에서 뽑고, 옛 버전 텍스트를 패치하지 않는다.
2. **사용자가 구술한 흐름은 보존한다.** 구조와 단어를 최대한 살리고 문장만 다듬어 의도를 녹인다. 구술을 그대로 옮기거나 재창작·멋내기를 하지 않는다.
3. **사실 검증.** 하지 않은 일을 쓰지 않는다. 애매하면 코드·문서에서 확인하거나 사용자에게 묻는다.
4. **글자수는 node로 센다** (`wc -m`은 한글 부정확):
   `node -e "const s=require('fs').readFileSync('f.txt','utf8').trim();console.log([...s].length)"`
   폼 제한은 보통 공백 포함. 400자 제한을 억지로 채우지 않는다.

항목별 세부 설명은 `references/composition.md`의 §4에 있다.

## 5. 제출 전 셀프 체크

초안 완성 후 아래를 훑고 나서 보여준다. 하나라도 걸리면 고치고 나서.

- [ ] 소리 내 읽으면 사람이 말하듯 흐르는가 (punch line·여운 마무리 없음)
- [ ] 각 문장이 앞 문장을 받아 이어지는가 (뚝뚝 끊긴 평문 나열 없음)
- [ ] 짧은 문장이 혼자 서 있지 않은가 (앞에 결론만 던지고 뒤에서 설명 ✕ / 끝을 짧게 끊어 마무리 ✕)
- [ ] 감정·상태 명사가 주어 자리에 앉아 있지 않은가
- [ ] 데이터·시각·시스템이 동사의 주어가 되어 있지 않은가 (주어는 사람·코드·밤 정리 같은 행위자)
- [ ] 짝대기 · 괄호 보충 · 부제 · 선나열후회수 · 따옴표 강조 없는가 (기능 문서의 캐릭터 대사 인용은 작은따옴표)
- [ ] 하지 않는 일을 문장 앞에 세우고 하는 일을 뒤에 붙인 문장이 없는가 (`~하지 않아서 ~합니다` ✕)
- [ ] 타이틀·라벨이 전부 명사구인가 (`~다` 종결 ✕ / 의문형 ✕ / `~하면` 조건절 종결 ✕ / 설명 문장을 `~것`으로 접은 제목 ✕)
- [ ] 제목과 이름만 보고 무엇을 다루는지 알 수 있는가 (의도·있는 일·방식 같은 넓은 말로 지은 이름 ✕)
- [ ] 정의 문장에 예시를 끼워 붙이거나, 앞 내용을 한 번 더 설명하는 부연으로 문단을 마무리하지 않았는가
- [ ] 의인화·문학적 어휘, 압축 조어, 독자가 모를 용어 없는가
- [ ] 구조를 층·축·구멍·배선으로 부르거나 추상적인 일을 물리 동작(부딪히다·새어 나가다·가르다·흘리다·닫다·오르다)으로 쓴 데가 없는가
- [ ] 이미 쓰는 말을 억지로 한국어로 바꾼 데가 없는가 (키→열쇠, 플러팅→수쓰기 류)
- [ ] 이력서·JD·이전 버전 문장을 그대로 가져온 데 없는가
- [ ] 낯선 개념이 소개 없이 등장하지 않는가
- [ ] 한 줄 설명에서 핵심이 맨 앞에 있는가 (부가 설명이 앞자리를 차지하지 않았는가)
- [ ] 내부 작업 용어·진행 상태(이관·개편·현 구현·정식본)가 남아 있지 않은가
- [ ] 뜻을 뭉갠 말(잇는다·접는다·어긋남·칸)이 없는가
- [ ] 수량을 말로 풀어 쓴 데(두셋·서넛·두세·두어)가 없는가
- [ ] 날짜는 7/3, 시각은 19:40 형식인가
- [ ] 팩트가 전부 실제 한 일인가 / 글자수 확인했는가
