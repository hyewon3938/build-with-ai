# writing — AI 말투·번역투 필터

> 2026-06~08 README·설계 문서·각종 제출 폼 작업에서 사용자가 준 문체 피드백을 전수 수집해 패턴화한 것.
> 대상: 사람이 읽는 한국어 산문 전부 — 채팅 답변, 설계 문서, HTML·도식에 넣는 문구와 카드 제목까지 포함. 코드 주석은 대상 아님. 화면용 짧은 라벨이라고 예외가 되지 않는다 (2026-08-25 설계 허브 카드 문구에서 위반이 반복돼 명시).
> 사용법: 초안을 쓰기 **전에** §1~3을 머리에 놓고 쓰고, 쓴 **후에** §5 셀프 체크를 돌린 다음 보여준다.

## 0. 기본 톤

담백 · 존댓말(지원서·이력서) · show-don't-tell · 두괄식. 형용사로 주장하지 않고 사실과 구조로 보여준다.
**멋있는 문장을 만들려는 순간이 가장 위험하다.** 실제 거절 사유 1위가 "너무 과해", "너무 문학적", "AI스러워"였다. 잘 쓴 문장이 아니라 사람이 말하듯 흐르는 문장이 목표다.

## 1. 문장 구조 — 금지 패턴 (전부 실제 지적 사례)

### 1-1. 짧은 단정 꼬리문장 · 여운 마무리
"~가 아니다." 식으로 짧게 끊어 강조하거나, 짧은 문장으로 멋지게 마무리하는 영어식 punch line.
- ✕ 외로움은 답을 못 들어서 생기는 게 아니다. 잘 대답해주는 상대가 있다고 채워지지 않는다.
- ✕ 그런 순간이 오면 된다. / 이 경험은 만들어진 것이다. / 지금도 매일 돌아갑니다.
- ○ 앞 문장에 이어 붙이거나 보통 길이의 서술로 끝낸다: "현재까지 매일 사용 중인 시스템입니다."

### 1-2. 짝대기(—)·콜론 뒤 임팩트 문장, 편집자적 부제
- ✕ 기준은 하나다 — 유저가 이 존재의 메시지를 기다리게 되는가.
- ✕ '정직한 검증 한계' '(발굴 아닌 검증)' 같은 부제·괄호 라벨 장식.
- ○ 쉼표로 잇거나 문장으로 푼다. 부제는 달지 않는다.

### 1-3. 선나열-후회수 화법 (대표적 번역투)
앞에 요소를 줄줄 나열해 놓고 마지막에 한 번에 받는 구조.
- ✕ 답장이 빨라지고 느려지는 것도, 먼저 건네는 말도 모두 그 삶에서 나옵니다.
- ○ 캐릭터는 자기 삶을 기반으로 답장 텀과 대화 소재가 정해집니다.

### 1-4. 재료 문장 이어붙이기
이력서 불릿·JD 문장·이전 버전 문서를 그대로 이어 붙이면 바로 티가 난다 ("줄줄이 이어붙인 느낌").
- 문장마다 판단(왜·그래서)이 담기고, 앞 문장을 받아 이어져야 한다. 조사 하나로도 잇는다:
  "고도화하는 과정을 반복해왔습니다" → "고도화하는 과정도 반복해왔습니다".
- JD 문구는 같은 자리에 같은 단어를 쓰되(검색 매칭), 문장 자체를 복사하지 않는다.

### 1-5. 부정 후 긍정 ("~가 아니라 ~다")
- ✕ 한 번에 큰 감정을 주는 게 아니라, 일상에 스며들 때 애착이 생긴다.
- ○ 한 번에 큰 감정을 주는 것보다는 일상에 계속 함께할 때 애착이 생긴다. (부정 대신 비교로 순화)

### 1-6. 어중간한 종결
- 명사형·나열형으로 끝내지 않는다: "케이스로." → "케이스로 처리." / "유지가 어려워짐" → "유지가 어려워져 체계로 관리".
- 이유 설명("~하기 때문이다")보다 결과 통보("~하도록 구성했습니다", "~에 넣었습니다")가 기본형.
- **시스템을 주어로 한 순수 현재형 종결만 이어지면 번역투로 읽힌다.** "관리가 복잡해지지 않습니다", "새벽에 정리해 업데이트합니다"처럼 결과를 현재형으로만 서술하지 말고, 만든 사람이 드러나는 종결("~하지 않도록 구성했습니다", "~하도록 해뒀습니다")을 주된 표현으로 쓴다.

### 1-7. 문장형 타이틀 · 압축 조어 라벨
타이틀과 불릿 라벨은 짧은 명사구로, 읽기 전에 내용이 예측돼야 한다.
- ✕ 문장형: '먼저 말을 걸고, 답이 없으면 연락을 멈춘다'
- ✕ 압축 조어(단어를 그냥 붙임): '시간 3층 구조' '답장행동' '선톡 5종' '상시 가동'
- ○ '3계층 기억 구조' + 친절한 설명. 압축이 안 되면 설명으로 전부 잇는다.
- 어필성 타이틀 금지: '1인 풀스택' 같은 자기 홍보 라벨 ✕ → '인프라 구성' 같은 실무 명칭.
- **타이틀·라벨·범례·표 머리글은 `~다`로 끝내지 않는다** (2026-08-25 설계 허브 지적). 문장 종결형을 짧은 라벨에 쓰면 미완성 문장처럼 읽힌다. 명사나 명사형으로 끝낸다.
  - ✕ 코드가 적는다 → ○ 코드가 자동 기록 / ✕ 모델이 만든다 → ○ 하루 한 번 모델이 생성
  - ✕ 오늘 계획을 만든다 → ○ 오늘 계획 생성 / ✕ 계획대로 보낸 시간은 적지 않는다 → ○ 계획대로 보낸 시간은 기록 없음
  - **수동태 라벨도 금지.** ✕ 대화 중에 적힌다 → ○ 대화를 통해 업데이트 (행위자를 숨긴 채 당하는 꼴로 쓰지 않는다)
  - 적용 범위는 카드 제목, 부제, 박스 제목, 박스 아래 한 줄 설명, 범례, 표 머리글, 각주 한 줄. 툴팁·본문처럼 여러 문장이 이어지는 산문은 평서형 그대로 둔다.
- **의문형 타이틀 금지** (2026-08-26 설계 허브 지적, 같은 지적이 여러 차례 반복돼 명시). 제목 자리에 질문을 쓰면 번역투로 읽히고, 답을 읽기 전까지 무슨 내용인지 알 수 없다. 질문의 답을 명사구로 바꿔 단다.
  - ✕ 왜 값으로 바꾸나 → ○ 값으로 바꾸는 이유 / ✕ 왜 두 단어인가 → ○ 두 단어 조합의 키
  - ✕ 어떻게 고르나 → ○ 고르는 방법 / ✕ 몇 줄까지 넣나 → ○ 프롬프트에 넣는 순서와 개수
  - ✕ 어느 항목 것인가 → ○ 저장 항목 사이의 순서 / ✕ 언제 것인가 → ○ 같은 항목 안의 순서
- **조건절로 끝나는 라벨도 문장형이다.** `~하면`, `~오면`처럼 뒷말이 잘린 꼴로 끝내지 않고 `~할 때`, `~한 연락`처럼 명사로 닫는다.
  - ✕ 유저가 붙잡으면 → ○ 유저가 붙잡을 때 / ✕ 자는 시간에 연락이 오면 → ○ 자는 시간에 온 연락
  - ✕ 각본이 늦으면 → ○ 각본이 늦어질 때 / ✕ 유저가 오래 답이 없으면 → ○ 유저가 오래 답이 없을 때

### 1-8. 괄호 보충 설명
- ✕ (이벤트와 컨디션이 인과로 엮여 있다)
- ○ 문장에 녹인다: "각 이벤트는 서로 인과 관계를 형성하며, 회식이 있던 다음 날엔 피곤해하는 식으로 나타납니다."

### 1-9. 결론 먼저 짧게 던지고 뒤에서 설명하기 (영어 문단 구조)

한 문장으로 결론을 툭 세우고 다음 문장에서 근거를 붙이는 topic sentence + supporting sentence 구조. 한국어로 옮기면 바로 번역투·AI 말투로 읽힌다. **이유와 결론을 한 문장에 묶는다.**
- ✕ 그 자리를 지금 챗봇이 채우기엔 부족했습니다. 유저가 먼저 말을 꺼내야 하고, 며칠 만에 말을 걸면 지난 이야기를 오늘 처음 하듯 받습니다.
- ○ 지금 챗봇은 유저가 먼저 말을 꺼내야 하고 며칠 만에 말을 걸면 지난 이야기를 오늘 처음 하듯 받아서, 그 자리를 채우기엔 부족합니다.
- ✕ 답장 텀도 일정마다 지정하지 않고 두 태그 조합으로만 정했습니다. 일정이 늘수록 하나하나 관리하기 어려워지기 때문입니다.
- ○ 답장 텀은 일정마다 지정하면 종류가 늘수록 관리하기 어려워져서, 두 태그의 조합으로만 정했습니다.
- §1-1(짧은 단정 꼬리문장)과 한 쌍이다. 1-1은 문단 끝, 1-9는 문단 앞. **짧은 문장이 혼자 서 있으면 앞뒤 어느 쪽이든 의심한다.**
- 예외: 문단 첫 도입 한 문장(예: `텔레그램으로 대화합니다.`)도 뒤 문장과 이을 수 있으면 잇는다. 끊어야만 하는 이유가 없으면 잇는 쪽이 기본.

### 1-10. 감정·상태 명사를 주어 자리에 앉히기

사람이 하는 일을 마음·느낌·감각 같은 추상 명사가 대신 주어가 되는 번역투. **사람을 주어로 되돌린다.**
- ✕ 연결이 그리운 마음은 남습니다. / 사람과 이어져 있다는 느낌은 남아 있습니다.
- ○ 사람과 이어지는 건 여전히 그리워합니다.
- ✕ 흥미가 초반에 붙들리지 않을 수 있습니다. → ○ 초반에 흥미를 붙들지 못할 수 있습니다.
- ✕ 내일 다시 찾을 이유는 남지 않는다. → ○ 다시 찾아올 이유가 없어 도구로만 쓰다 만다. (이유·마음·느낌이 `남다/사라지다`의 주어가 되어 문장을 끝내지 않는다 — 주어는 사람·유저)
- §2-1(의인화)과 다르다. 2-1은 사물이 살아 움직이는 것, 1-10은 감정·상태가 주어 자리를 차지하는 것.

## 2. 어휘 — 피하는 단어

### 2-1. 의인화·추상·문학적 표현
사물·개념을 주어로 살아 움직이게 하지 않는다. 실무적이고 직관적인 동사로 바꾼다. 실제 지적·교정례:
닿게 하다→보여주다 · 스미다→녹아들다 · 시선이 사라진다→봐줄 사람이 없다 · 하루가 흘러가는 감각 ✕ · 가벼운 포착 ✕ · 밤 응고→데이터 정리 · 다른 층→다른 결 · 통계에 태운다·통계를 돌리다 ✕ · 그 아래 깔려 있다 ✕ · 느낌이 옅어지다→(직관적으로) · 기계의 표식→사람 같지 않은 느낌 · 발명하지 않는다→지어내지 않는다 · 이 글을 쓰는 지금도 이어지는 중이다→매일 대화 중입니다 · 무너지기 전에(과함)→미리 개선할 수 있게 · 아직 닫히지 않은 이야깃거리→대화 소재 · 붙들고 있다→고민하다/다루다 · 프롬프트에 싣다→전달하다/넣다 · 갱신하다→정리해 업데이트하다 · 조건을 적다(사고 과정을 행위로 연출)→생각하다/정리하다 · 잠깐 켜는 도구로 남다→외로울 때만 잠깐 쓰다 말다(사물을 주어로 세워 `남는다`고 쓰지 않는다) · 깔다(각본을 깐다·한 달치가 깔린다)→만들다/미리 만들어 두다 · 새다(다른 칸으로 샌다·사건이 새 들어간다)→잘못 들어가다/섞여 들어가다 — 깔다·새다류 공간 비유는 시스템 동작 설명에 쓰지 않는다(2026-08-24 지적). 동사뿐 아니라 층·축·구멍·배선 같은 명사도 같은 부류다(§2-8).

### 2-2. 일상에서 안 쓰는 단어·독자가 모를 용어
품이 든다 · 짚다 · 관측 · 간주하다 · 호혜적 · 청사진 · 검정(통계 용어) · 원시 로그(→기록) · 배치가 돌다(→새벽에 정리한다처럼 결과로) · 클램프 · fire-and-forget · p80 · 재료(데이터를 가리킬 때 → 데이터) · 실물(→ 예시, 실제 값) · 프런트매터(→ 파일 맨 위 설정 부분) …
- 낯선 용어는 풀어 쓰거나 뺀다. 기준: "내가 만들었는데도 헷갈리면 그게 문제". 초등학생이 처음 읽어도 맥락이 잡혀야 한다.
- **다만 사람들이 이미 그 말로 쓰고 있는 용어와 외래어는 풀어 쓰지 않는다**(§2-7). 이 규칙을 넓게 적용해 키를 열쇠로, 플러팅을 수쓰기로 바꾸는 과잉 번역이 실제로 나왔다.
- **수량은 숫자로 쓴다.** 두셋·서넛·두세·두어·한둘·서너 명처럼 말로 풀지 않고 2~3개, 3~4명, 2~3줄로 쓴다 (2026-08-24 지적, 2026-08-25 재지적 — 규칙이 있는데도 설계 문서 3곳에서 다시 나왔다). 저장된 값을 그대로 보여주는 예시 자리는 대상이 아니다.

### 2-3. 구어체 침투
"한 달치를 미리 깔아" → "한 달치를 미리 정해두고" · "~모으려고," ✕ · "거기서" 같은 지시어 ✕ · "회의는 이렇게 병원은 저렇게 식으로" ✕.
편한 구어는 담백한 문어로 바꾼다.
- **판단을 `보다`로 받지 않는다.** `~라고 봤습니다`·`~로 본다` → `~라고 생각했습니다`. `보다`로 받으면 한 발 물러선 관찰자처럼 읽혀서, 정작 그렇게 판단한 사람이 흐려진다. 리드미 1인칭 초안(`~이라고 봤다`)을 지원서 존댓말로 옮길 때 특히 자주 그대로 남는다.

### 2-4. 가상 대사·따옴표 강조
- ✕ '요즘 너무 늦게 자더라' 한마디로 방향을 잡는데
- 작은따옴표 가상 대사, 쌍따옴표 키워드 띄우기 자체가 AI스럽다. 예시 문장이 필요하면 따옴표 없이 서술로: "수면이 부족한 날은 일정 달성률이 낮을 것이다 같은 생활 통념 기반 가설은 미리 만들어두고".

### 2-5. 데이터·시각·시스템을 동사의 주어로 세우는 의인화 (2026-08-25 설계 허브 지적)

설계 문서·도식 문구에서 데이터나 시각이 사람처럼 행동하는 문장. 주어를 사람·코드·밤 정리 같은 실제 행위자로 되돌리고, 목적어를 생략하지 않는다. 전부 실제 지적 사례:
- ✕ 지금 시각이 계획과 실제를 가른다 / 지금 시각이 읽는 경계다 → ○ 코드가 현재 시각을 기준으로, 지난 시간은 실제 기록으로 읽고 남은 시간은 계획으로 읽는다
- ✕ 하루가 흐르면 실제가 그 위에 쌓인다 → ○ 하루를 보내면서 계획과 다르게 지낸 시간이 생기면 코드가 실제 기록에 적는다
- ✕ 태그가 잡은 것을 판정 없이 쌓는다 → ○ 모델이 답장에 표시를 붙이면 코드가 그 문장을 그대로 적어 둔다 (주어·목적어를 생략한 채 동사만 남기지 않는다)
- ✕ 진행 중인 일이 들고 있다 · 실제로 산 하루가 그 위를 덮어쓴다 · 기억이 원문에 기대지 않는다
- '경계' '실제' 같은 압축 명사를 정의 없이 제목·문장에 쓰지 않는다. 처음 나오는 낱말은 무엇인지 한 문장으로 소개한 뒤 쓴다.

### 2-6. 뜻을 뭉갠 동사·명사 (2026-08-25 설계 허브 지적)

짧게 만들려다 뜻이 뭉개진 말. 읽는 사람이 무슨 일이 벌어지는지 그릴 수 없으면 실패다. **정확한 표현이 길면 긴 쪽을 쓴다.**
- ✕ 이벤트끼리 원인과 결과로 잇는다 → ○ 연결한다
- ✕ 일정을 접는다 → ○ 취소한다 / 미룬다 (무엇을 어떻게 했는지가 사라지는 축약)
- ✕ 어긋남 · 어긋난 블록 → ○ 계획과 달라진 부분
- ✕ 나의 쌓인 사실 → ○ 대화에서 추가된 내 정보
- ✕ 활동과 두 태그 → ○ 태그 두 가지의 이름을 그 자리에서 밝힌다 (독자는 태그가 무엇인지 아직 모른다)
- ✕ 정식 칸 · 열세 칸 → ○ 저장 항목 (내부 문서에서만 쓰는 말을 밖으로 내보내지 않는다)
- **이름은 핵심으로 붙인다.** ✕ 오래된 일기(오래된 것이 핵심이 아니다) → ○ 지난 일기. 부차적인 성질을 이름에 넣으면 독자가 핵심을 그쪽으로 잡는다.

### 2-7. 과잉 번역 — 이미 쓰는 말 억지로 바꾸기 (2026-09-12 지적)

§2-2의 낯선 용어 풀어쓰기를 넓게 적용하면 반대 방향으로 넘어가서, 한국어를 쓰는 사람들이 이미 그 말로 부르고 있는 것까지 바뀐다. 실제로 `중복 키 제거`가 `중복 열쇠 제거`로, `플러팅`이 `수쓰기`로 나왔다. **사람들이 그 자리에서 실제로 쓰는 말을 쓴다.**

**기술 용어** — 키 · 값 · 인덱스 · 캐시 · 커밋 · 브랜치 · 머지 · 스키마 · 마이그레이션 · 쿼리 · 토큰 · 프롬프트 · 타임아웃 · 롤백 · 배치 · 훅 · 심링크 · 레지스트리 · 태그 · 페이로드 · 파서. 영어 약어와 제품 이름도 그대로 둔다.

**일상에 들어온 외래어** — 플러팅 · 컨디션 · 리액션 · 텐션 · 케미 · 루틴 · 타이밍 · 이벤트 · 캐릭터 · 유저 · 피드백 · 스트레스 · 메시지 · 서비스 · 데이터.

- ✕ 수쓰기 → ○ 플러팅
- ✕ 몸 형편 · 몸 상태 매김 → ○ 컨디션
- ✕ 때맞춤 → ○ 타이밍
- ✕ 되돌림말 → ○ 피드백
- ✕ 중복 열쇠 제거 → ○ 중복 키 제거
- ✕ 값 담는 틀 → ○ 스키마
- ✕ 되돌리기 실행 → ○ 롤백
- ✕ 꼬리표 → ○ 태그

**판단 기준.** 바꾼 말을 소리 내 읽었을 때 그 자리에서 그 단어를 그렇게 쓸 사람이 없으면 원래 말이 맞다. §2-2가 막는 일상에서 안 쓰는 한자어(관측·간주하다·품이 든다)와 여기서 막는 아무도 안 쓰는 한국어 조어(수쓰기·열쇠·되돌림말)는 같은 기준에 걸리는 반대 방향 실패다. 규칙을 두 개로 외우지 말고 기준 하나로 정한다.

**외래어라서 남기는 것이 아니다.** 그 말을 쓰기 때문에 남기는 것이라, 더 많이 쓰이는 한국어 짝이 있으면 한국어를 쓴다. 컨텍스트보다 맥락, 캔슬보다 취소, 체크보다 확인, 이슈(문제라는 뜻일 때)보다 문제다.

**독자가 모르는 외래어는 남기는 대상이 아니다.** 이 규칙은 읽는 사람이 아는 말에만 적용된다. 프런트매터·페이로드·파서처럼 그 분야 사람만 쓰는 말을 외부 문서에 그대로 내보내면 §2-2에 걸린다. 기술 용어 목록도 개발자가 읽는 문서에서만 그대로 두고, 읽는 사람이 개발자가 아니면 풀어 쓰거나 한 번 소개한다. 실제로 포트폴리오용 문서에 `프런트매터`를 소개 없이 써서 이게 무슨 말이냐는 지적을 받았다(2026-09-12).

풀어 쓸 대상은 우리끼리 만든 조어와 소개 없이 쓴 압축 명사뿐이다(§2-5·§2-6). 설계 대화에서 개념에 이름을 붙일 때 특히 자주 나오므로, 새 이름이 필요한 개념인지 이미 이름이 있는 개념인지 먼저 확인한다. 새로 지을 때도 대응하는 표준 용어를 한 번은 같이 밝힌다.

### 2-8. 구조를 공간·물건 이름으로 부르기 (2026-09-12 지적)

분류·설정·문서 구조를 층·축·구멍·배선처럼 공간이나 물건 이름으로 부르는 말. 하나만 보면 뜻이 통하는데 문서 하나에 여러 개가 모이면 사람이 쓴 글로 읽히지 않는다. **몇 가지인지, 어디에 적었는지, 무엇이 안 되는지를 그대로 센다.** 전부 실제 지적 사례다.

- ✕ 규칙을 두 층으로 가르기 → ○ 규칙을 두 가지로 나누기
- ✕ 상시 층 · 또 하나의 축은 과잉이다 → ○ 항상 적용하는 규칙 · 또 하나는 과잉이다
- ✕ 남은 구멍은 로드였다 · 이 구멍이 더 커졌다 → ○ 남은 문제는 로드였다 · 이 문제가 더 커졌다
- ✕ 상시 적용되게 배선했다 → ○ 모든 세션에 적용되게 설정했다
- ✕ 규칙끼리 부딪힌 자리 → ○ 규칙끼리 충돌한 부분
- ✕ 목록에 없는 말이 새어 나간다 → ○ 목록에 없는 말이 그대로 나온다
- ✕ 기준 하나로 가른다 → ○ 기준 하나로 정한다

추상적인 일을 물리 동작으로 쓰는 것(부딪히다·새어 나가다·가르다)도 같은 부류라 §2-1의 깔다·새다와 이어진다. 다만 눈에 보이는 실제 공간·물건을 가리킬 때는 비유가 아니므로 그대로 쓴다. `자리`도 주어 자리처럼 실제 위치를 가리키면 그대로 쓰고, 제목에서 `~한 자리`로 쓰면 무엇을 말하는지 밝히거나 부분·경우로 바꾼다.

## 3. 구성 — 흐름

- **두괄식.** 핵심 먼저, 근거·예시는 뒤. 문장 앞의 꾸미는 말을 길게 늘어놓지 않는다.
- **낯선 개념은 등장 전에 소개.** 독자가 아직 모르는 단어(블록·교체·가설 등)를 설명 없이 쓰지 않는다. "갑자기 가설이 나오니까 낯설어."
- **억지 연결 금지.** "~하는 구조라, ~와 연결지점이 많다고 생각합니다"처럼 강제로 잇지 않는다. 동기 → 사실 → 연결 순서로 자연스럽게 겹치게 한다.
- **같은 단어 반복·가짜 연결 금지.** 이웃 문장에 같은 단어가 연달아 나오면 지시어로 받거나 문장을 합친다(`외로움도 흔해졌고 ~ 외로움을 느낀다고 답했다` → `~ 절반 가까이가 그렇다고 답했다`). `~하고/~해서`로 이을 때는 실제 인과·근거 관계인지 확인 — 나열처럼 이으면 관계가 없어 보인다.
- **전제와 뒤 내용의 아귀 맞추기.** 앞에서 세운 전제가 바로 뒤 내용과 맞물려야 한다. `답을 잘 해주는 상대가 있다고 외로움이 채워지진 않는다` 뒤에 답도 제대로 못 이어가는 챗봇 이야기가 오면 전제가 헛돈다.
- **구구절절 금지.** 조건·부연을 다 담으려는 긴 문장은 나누거나 버린다. 이해를 돕지 못하는 예시는 노이즈다.
- **당연한 내용 삭제.** 설명할 가치가 없는 당연한 설계("추출은 답장 후에 시작해 속도에 영향 없음")는 뺀다. 내용이 많은 것보다 임팩트가 중요하다.
- **개발일지 화법 금지.** "원래 이랬는데 이렇게 고쳤다"가 아니라 결과만 서술한다. 문서는 다 만들어진 상태를 기준으로 쓴다. 다만 **지우되 버리지는 않는다** — 개선 전후 비교는 따로 한곳에 모아 두고, 본문에서는 뺀다 (2026-08-25).
- **내부 작업 용어와 진행 상태를 문서에 쓰지 않는다** (2026-08-25 설계 허브 지적). 이관, 개편, 정식본, 현 구현, 새 구조, 이관 때 채움 같은 말은 우리 작업 일정을 아는 사람만 읽을 수 있다. 예시에도 프로젝트 사정을 주석으로 달지 않는다 — 예시 자리에는 값만 쓴다.
- **한 줄 설명은 핵심을 앞에 둔다** (2026-08-25 설계 허브 지적). 라벨 한 줄이 여러 사실을 담을 때, 독자가 알아야 할 핵심이 맨 앞이고 나머지는 뒤다. 아직 소개하지 않은 고유 이름을 앞자리에 놓으면 그 이름부터 걸린다.
  - ✕ 밤 정리가 다시 써서 하루 동안 같음 → ○ 하루 동안 고정 · 매일 새벽에 그날 내용으로 갱신
  - ✕ 캐릭터 쪽과 유저 쪽 사람들, 누구 쪽인지 표시 → ○ 캐릭터의 주변 인물과 유저의 주변 인물을 함께 저장한다. 인물마다 누구의 지인인지도 표시해 둔다
- **날짜와 시각 표기.** 날짜는 7/3, 시각은 19:40으로 쓴다. 7-03처럼 쓰면 날짜인지 시각인지 구분이 안 된다 (2026-08-25).
- **자기 작업 ↔ 회사 직접 동급 비교 금지.** "내 것이나 회사 것이나 비슷하다"는 건방져 보인다 → "제가 해온 작업과 결이 비슷하다고 느꼈습니다"처럼 내 경험을 주어로.
- **동작 설명은 장면이 그려지게, 마무리는 설계 귀결로.** 제품 동작을 요약 서술("먼저 연락한다")로 반복하지 말고 독자가 그림을 그릴 수 있는 구체 행동으로 나열한다(출근 전에 연락해 오고, 물으면 실제 하고 있는 일을 답하고). 마지막 문장이 상황 묘사로만 끝나면 만든 사람이 사라진다 — 그 결과가 나오도록 설계했다는 인과(~해 두기 때문에 ~한다)까지 담는다.
- **핵심 주장을 관형절 속에 묻지 않는다.** `~할 가능성은 지켜봐야 합니다`처럼 정작 하고 싶은 말(가능성이 있다)이 긴 명사구의 수식어로 들어가면 핵심이 뒤로 밀린다. `~할 수도 있어, 나중에 개선할 부분입니다`처럼 주장을 본동사로 먼저 말하고 대응을 잇는다.
- **같은 구조의 문장을 연달아 쓰지 않는다.** "~하면 ~해서, ~하게 했다"(문제→해결) 같은 틀이 연속 두 문장에 반복되면 기계적으로 읽힌다. 둘 중 하나를 뒤집어 설계 먼저·효과 뒤("~으로만 정해, ~하지 않습니다")로 쓰는 식으로 변주한다.
- **한계 서술은 결핍 나열이 아니라 인지+우선순위로.** "~가 없고, ~뿐이라" 식으로만 쓰면 대책 없어 보인다. 지금 무엇에 집중하고 있어 이것들은 그다음 순서라는 틀을 앞에 세우고, 한계마다 계획(모이면 검증 시작, 커지면 이어서 최적화)으로 닫는다. 솔직함은 유지하되 방치로 읽히지 않게.

## 4. 프로세스 규칙

1. **원본 소스에서 새로 뽑는다.** 프로젝트 문구의 원본은 해당 프로젝트 README → 그다음이 이력서 → 지원서·프로필은 이력서에서 뽑는다. 옛 버전 텍스트를 패치하지 않는다 — 패치 반복은 "덕지덕지"가 된다. 덕지덕지 조짐이 보이면 부분 수정 대신 전체 재구성을 제안한다.
2. **사용자가 구술한 흐름은 보존한다.** 사용자가 말로 흐름을 불러주면 그 구조와 단어를 최대한 살리고 문장만 다듬는다. 단, 구술을 그대로 옮기지도 않는다 — 의도를 문장에 녹인다. 재창작·멋내기 금지.
3. **사실 검증.** 하지 않은 일을 쓰지 않는다. 애매하면 코드·문서에서 확인하거나 사용자에게 묻는다. 과장은 면접에서 본인을 곤란하게 만든다.
4. **글자수는 node로 센다** (`wc -m`은 한글 부정확):
   `node -e "const s=require('fs').readFileSync('f.txt','utf8').trim();console.log([...s].length)"`
   폼 제한은 보통 공백 포함. 400자 제한을 억지로 채우지 않는다.

## 5. 제출 전 셀프 체크

초안 완성 후 아래를 훑고 나서 보여준다. 하나라도 걸리면 고치고 나서.

- [ ] 소리 내 읽으면 사람이 말하듯 흐르는가 (punch line·여운 마무리 없음)
- [ ] 각 문장이 앞 문장을 받아 이어지는가 (뚝뚝 끊긴 평문 나열 없음)
- [ ] 짧은 문장이 혼자 서 있지 않은가 (앞에 결론만 던지고 뒤에서 설명 ✕ / 끝을 짧게 끊어 마무리 ✕)
- [ ] 감정·상태 명사가 주어 자리에 앉아 있지 않은가
- [ ] 데이터·시각·시스템이 동사의 주어가 되어 있지 않은가 (주어는 사람·코드·밤 정리 같은 행위자)
- [ ] 짝대기 · 괄호 보충 · 부제 · 선나열후회수 · 따옴표 강조 없는가
- [ ] 타이틀·라벨이 전부 명사구인가 (`~다` 종결 ✕ / 의문형 ✕ / `~하면` 조건절 종결 ✕)
- [ ] 의인화·문학적 어휘, 압축 조어, 독자가 모를 용어 없는가
- [ ] 구조를 층·축·구멍·배선으로 부르거나 추상적인 일을 물리 동작(부딪히다·새어 나가다·가르다)으로 쓴 데가 없는가
- [ ] 이미 쓰는 말을 억지로 한국어로 바꾼 데가 없는가 (키→열쇠, 플러팅→수쓰기 류)
- [ ] 이력서·JD·이전 버전 문장을 그대로 가져온 데 없는가
- [ ] 낯선 개념이 소개 없이 등장하지 않는가
- [ ] 한 줄 설명에서 핵심이 맨 앞에 있는가 (부가 설명이 앞자리를 차지하지 않았는가)
- [ ] 내부 작업 용어·진행 상태(이관·개편·현 구현·정식본)가 남아 있지 않은가
- [ ] 뜻을 뭉갠 말(잇는다·접는다·어긋남·칸)이 없는가
- [ ] 수량을 말로 풀어 쓴 데(두셋·서넛·두세·두어)가 없는가
- [ ] 날짜는 7/3, 시각은 19:40 형식인가
- [ ] 팩트가 전부 실제 한 일인가 / 글자수 확인했는가
