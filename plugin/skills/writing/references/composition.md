# writing §3·§4 구성과 프로세스 세부 규칙

SKILL.md §3·§4 항목마다 실제 지적 사례와 교정 예시, 지적 경위를 전부 모았고, 항목 이름과 번호는 SKILL.md와 같다.

## 3. 구성 — 흐름

- **두괄식.** 핵심 먼저, 근거·예시는 뒤. 문장 앞의 꾸미는 말을 길게 늘어놓지 않는다.
- **낯선 개념은 등장 전에 소개.** 독자가 아직 모르는 단어(블록·교체·가설 등)를 설명 없이 쓰지 않는다. "갑자기 가설이 나오니까 낯설어."
- **억지 연결 금지.** "~하는 구조라, ~와 연결지점이 많다고 생각합니다"처럼 강제로 잇지 않는다. 동기 → 사실 → 연결 순서로 자연스럽게 겹치게 한다.
- **같은 단어 반복·가짜 연결 금지.** 이웃 문장에 같은 단어가 연달아 나오면 지시어로 받거나 문장을 합친다(`외로움도 흔해졌고 ~ 외로움을 느낀다고 답했다` → `~ 절반 가까이가 그렇다고 답했다`). `~하고/~해서`로 이을 때는 실제 인과·근거 관계인지 확인 — 나열처럼 이으면 관계가 없어 보인다.
- **전제와 뒤 내용의 아귀 맞추기.** 앞에서 세운 전제가 바로 뒤 내용과 맞물려야 한다. `답을 잘 해주는 상대가 있다고 외로움이 채워지진 않는다` 뒤에 답도 제대로 못 이어가는 챗봇 이야기가 오면 전제가 헛돈다.
- **구구절절 금지.** 조건·부연을 다 담으려는 긴 문장은 나누거나 버린다. 이해를 돕지 못하는 예시는 노이즈다.
- **당연한 내용 삭제.** 설명할 가치가 없는 당연한 설계("추출은 답장 후에 시작해 속도에 영향 없음")는 뺀다. 내용이 많은 것보다 임팩트가 중요하다.
- **개발일지 화법 금지.** "원래 이랬는데 이렇게 고쳤다"가 아니라 결과만 서술한다. 문서는 다 만들어진 상태를 기준으로 쓴다. 다만 **지우되 버리지는 않는다** — 개선 전후 비교는 따로 한곳에 모아 두고, 본문에서는 뺀다 (2026-08-25).
- **내부 작업 용어와 진행 상태를 문서에 쓰지 않는다** (2026-08-25 설계 허브 지적). 이관, 개편, 정식본, 현 구현, 새 구조, 이관 때 채움 같은 말은 우리 작업 일정을 아는 사람만 읽을 수 있다. 예시에도 프로젝트 사정을 주석으로 달지 않는다 — 예시 자리에는 값만 쓴다.
- **한 줄 설명은 핵심을 앞에 둔다** (2026-08-25 설계 허브 지적). 라벨 한 줄이 여러 사실을 담을 때, 독자가 알아야 할 핵심이 맨 앞이고 나머지는 뒤다. 아직 소개하지 않은 고유 이름을 앞자리에 놓으면 그 이름부터 걸린다.
  - ✕ 밤 정리가 다시 써서 하루 동안 같음 → ○ 하루 동안 고정 · 매일 새벽에 그날 내용으로 갱신
  - ✕ 캐릭터 쪽과 유저 쪽 사람들, 누구 쪽인지 표시 → ○ 캐릭터의 주변 인물과 유저의 주변 인물을 함께 저장한다. 인물마다 누구의 지인인지도 표시해 둔다
- **날짜와 시각 표기.** 날짜는 7/3, 시각은 19:40으로 쓴다. 7-03처럼 쓰면 날짜인지 시각인지 구분이 안 된다 (2026-08-25).
- **자기 작업 ↔ 회사 직접 동급 비교 금지.** "내 것이나 회사 것이나 비슷하다"는 건방져 보인다 → "제가 해온 작업과 결이 비슷하다고 느꼈습니다"처럼 내 경험을 주어로.
- **동작 설명은 장면이 그려지게, 마무리는 설계 귀결로.** 제품 동작을 요약 서술("먼저 연락한다")로 반복하지 말고 독자가 그림을 그릴 수 있는 구체 행동으로 나열한다(출근 전에 연락해 오고, 물으면 실제 하고 있는 일을 답하고). 마지막 문장이 상황 묘사로만 끝나면 만든 사람이 사라진다 — 그 결과가 나오도록 설계했다는 인과(~해 두기 때문에 ~한다)까지 담는다.
- **핵심 주장을 관형절 속에 묻지 않는다.** `~할 가능성은 지켜봐야 합니다`처럼 정작 하고 싶은 말(가능성이 있다)이 긴 명사구의 수식어로 들어가면 핵심이 뒤로 밀린다. `~할 수도 있어, 나중에 개선할 부분입니다`처럼 주장을 본동사로 먼저 말하고 대응을 잇는다.
- **같은 구조의 문장을 연달아 쓰지 않는다.** "~하면 ~해서, ~하게 했다"(문제→해결) 같은 틀이 연속 두 문장에 반복되면 기계적으로 읽힌다. 둘 중 하나를 뒤집어 설계 먼저·효과 뒤("~으로만 정해, ~하지 않습니다")로 쓰는 식으로 변주한다.
- **한계 서술은 결핍 나열이 아니라 인지+우선순위로.** "~가 없고, ~뿐이라" 식으로만 쓰면 대책 없어 보인다. 지금 무엇에 집중하고 있어 이것들은 그다음 순서라는 틀을 앞에 세우고, 한계마다 계획(모이면 검증 시작, 커지면 이어서 최적화)으로 닫는다. 솔직함은 유지하되 방치로 읽히지 않게.

## 4. 프로세스 규칙

1. **원본 소스에서 새로 뽑는다.** 프로젝트 문구의 원본은 해당 프로젝트 README → 그다음이 이력서 → 지원서·프로필은 이력서에서 뽑는다. 옛 버전 텍스트를 패치하지 않는다 — 패치 반복은 "덕지덕지"가 된다. 덕지덕지 조짐이 보이면 부분 수정 대신 전체 재구성을 제안한다.
2. **사용자가 구술한 흐름은 보존한다.** 사용자가 말로 흐름을 불러주면 그 구조와 단어를 최대한 살리고 문장만 다듬는다. 단, 구술을 그대로 옮기지도 않는다 — 의도를 문장에 녹인다. 재창작·멋내기 금지.
3. **사실 검증.** 하지 않은 일을 쓰지 않는다. 애매하면 코드·문서에서 확인하거나 사용자에게 묻는다. 과장은 면접에서 본인을 곤란하게 만든다.
4. **글자수는 node로 센다** (`wc -m`은 한글 부정확):
   `node -e "const s=require('fs').readFileSync('f.txt','utf8').trim();console.log([...s].length)"`
   폼 제한은 보통 공백 포함. 400자 제한을 억지로 채우지 않는다.
