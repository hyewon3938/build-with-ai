# 커밋되는 문서 갱신

worktree 세션은 base 브랜치를 체크아웃할 수 없어서, 커밋되는 문서는 머지 전에 PR 브랜치에 넣는다. 해당 파일이나 폴더가 없는 프로젝트는 그 항목을 건너뛴다.

## ADR

이슈나 대기열 행에 ADR 작성이 있으면 만든다.

1. 번호는 `docs/adr/`의 가장 큰 번호 다음이다. `gh pr list --state open --json number,files`에서 `docs/adr/` 경로를 보고, 열린 PR이 이미 쓴 번호는 피한다.
2. `docs/adr/template.md`를 복사해 `docs/adr/NNNN-<제목>.md`를 만들고, 이슈나 설계 문서의 결정을 옮긴 뒤 구현하며 알게 된 세부를 보탠다.
3. `docs/adr/README.md` 인덱스에 한 줄 넣는다.
4. 구현과 같은 PR에 넣는다.

## 도메인 문서

`docs/domains/<도메인>.md`가 있고 이번 변경이 그 도메인 기능에 영향을 주면 갱신한다.

1. `git diff --name-only origin/<base>...HEAD`로 바뀐 파일을 보고 도메인을 찾는다. 대응이 모호하면 묻는다.
2. ``grep -n "TODO(`/build`)" docs/domains/<도메인>.md``로 설계 단계가 남긴 골격을 찾아 본문을 채우고 표시를 지운다. 골격이 없으면 이 단계에서 절을 만들고 그 사실을 완료 보고에 적는다.
3. 데이터 모델, 판정 로직, 명령어, 크론 시각, 흐름, 다음 단계와의 연결, 관련 ADR 가운데 이번 변경에 해당하는 것을 적는다.
4. 문서 끝에 파일 구조 블록이 있으면 새 파일을 넣는다.

## 기능 카탈로그

`docs/features.md`가 있으면 두 경우에 고친다.

- 사용자가 알아챌 기능, 명령어, 크론, 화면, API가 새로 생기면 기존 형식대로 항목을 넣는다. 기존 기능의 동작이 바뀌었으면 그 항목 설명을 고친다.
- 기능이나 모듈을 없앴으면 남은 흔적을 지운다. `git diff --name-status origin/<base>...HEAD`에서 D와 R 줄을 보고, 없앤 파일 이름, 표 이름, 기능 이름, 명령어로 `grep -rn '<키워드>' docs/features.md docs/domains/ docs/design-notebook/ README.md`를 돌린다. design-notebook 본문은 그대로 두고, 운영 중이라고 단정한 문장에만 시점을 적는다.

## 프로젝트 히스토리

`docs/project-history.md`가 있으면 마일스톤급 변화일 때만 한 줄 넣는다. 새 기능 출시, 아키텍처나 인프라 전환, 묶음 이슈의 단계 완료, 외부 청중에게 보여 줄 만한 변화가 기준이고, 형식은 `### YYYY-MM-DD: 제목 (#이슈, PR #번호)`이다. 버그 수정과 리팩토링은 PR과 커밋 메시지로 남긴다.

## 설계 노트

묶음 이슈의 마지막 세션이면 `docs/design-notebook/<묶음>.md` 마지막 절에 결과와 회고를 넣고, 맨 위에 단계마다 무엇을 했는지 한 문단으로 요약한다.

## 프로젝트 CLAUDE.md가 정한 문서

- 프로젝트 CLAUDE.md가 머지할 때 줄을 붙이라고 한 문서가 있으면 이 브랜치에서 붙인다. 머지한 뒤나 머지한 자리에서 붙이라고 적혀 있어도, base 브랜치에서 따로 고치면 그 한 줄 때문에 PR이 하나 더 생기므로 머지 전에 이 브랜치에 넣는다.
- CLAUDE.md 상태 절에 이 세션이 끝낸 항목이 있으면 같은 PR에서 지운다.
- 파일 맨 위 요약 주석이나 생성되는 색인처럼 커밋 훅이 검사하는 파일은 훅이 요구하는 명령을 돌려 함께 커밋한다.
