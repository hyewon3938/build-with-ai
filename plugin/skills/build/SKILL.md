# /build - 세션 구현 스킬

세션 하나는 이슈 1개, 브랜치 1개, PR 1개다. 대기열 파일 `LOCAL-SESSIONS.md`에서 세션 행을 읽고, worktree에서 구현한 뒤 리뷰와 PR과 머지를 거쳐 대기열과 배포 뒤 확인 목록까지 고친다.

## 입력

$ARGUMENTS

- 대기열에 같은 이름의 행이 있으면 그 행이 이번 세션이다. 상태가 머지 전 확인이면 6단계의 CI 확인부터 이어간다.
- 이슈 번호(`#N`)를 받으면 이슈 칸이 같은 행을 이번 세션으로 본다. 그런 행이 없으면 그 이슈를 요청으로 삼아 세션 하나를 연다.
- 계획서 경로를 받았거나, 대기열 없이 `.claude/plans/`에 계획서만 있으면 `references/plan-file.md`를 함께 따른다.
- 그 밖의 요청은 세션 하나로 본다. 프로젝트 CLAUDE.md가 이슈를 쓰라고 하면 이슈부터 만들고, 이슈를 쓰는지 알 수 없으면 묻는다.
- 인자가 없으면 대기열의 다음 세션은 `/next`로 연다고 알리고 끝낸다.

## 경로 규칙

메인 체크아웃은 `git worktree list --porcelain`의 첫 `worktree` 줄이다. 대기열, `LOCAL-TRACK.md`, `LOCAL-CONTEXT.md` 같은 LOCAL 파일은 worktree 안에서도 메인 체크아웃의 절대 경로로 읽고 고친다. worktree 안의 같은 이름은 심링크라서, 편집 도구가 임시 파일을 쓴 뒤 이름을 바꾸는 방식으로 저장하면 링크가 일반 파일로 바뀌어 고친 내용이 원본에 들어가지 않는다.

## 실행 흐름

### 1. 맥락

프로젝트 CLAUDE.md, 행이나 이슈가 가리키는 설계 문서의 해당 절, `LOCAL-CONTEXT.md`에서 이 세션에 필요한 절만 읽는다.

### 2. 시작 전 확인

아래 4가지를 확인한다. `/next`에서 넘어온 세션은 이 확인을 이미 거쳤으므로 3단계로 간다.

1. 여는 날짜: 행의 여는 날짜가 오늘보다 뒤면 걸린다. 날짜 대신 앞 세션 배포 뒤 며칠처럼 조건이 적혀 있으면 그 조건이 채워졌는지 확인하고, 확인할 수 없으면 걸린 것으로 본다.
2. 선행 세션: 선행 세션이 대기열에 남아 있으면 걸린다. 선행 칸이 배포까지 요구하면 배포 대기 표에 있어도 걸린다. 대기열과 배포 대기 표 어디에도 없는 세션은 끝난 것으로 본다.
3. 파일 겹침: 아래 두 목록이 행의 손댈 파일과 겹치면 걸린다.
   - `gh pr list --state open --json number,title,files`의 파일
   - 다른 worktree마다 `git -C <worktree> diff --name-only origin/<base>...HEAD`와 `git -C <worktree> status --porcelain`에 나온 파일
4. 모델: 행의 모델 칸이 지금 세션 모델과 다르면 걸린다. 지금 세션 모델은 시스템 프롬프트에 적힌 모델 이름에서 opus, sonnet 같은 계열만 떼어 비교하고, 행에 모델 칸이 없으면 넘어간다.

1~3 가운데 하나라도 걸리면 구현 전에 멈추고 걸린 까닭을 알린다. 4에 걸리면 구현 전에 멈추고, 행의 모델과 지금 모델을 알린 뒤 AskUserQuestion으로 지금 모델로 계속할지 앱에서 모델을 바꾼 뒤 계속할지 묻는다. 바꾼다고 답하면 사용자가 모델을 바꾸고 다시 말할 때까지 기다렸다가 4를 한 번 더 확인한다.

### 3. worktree 준비

`references/worktree.md`를 따른다. 준비가 끝나면 대기열 행의 상태를 진행 중으로 바꾼다.

### 4. 구현과 문서

- 행이나 이슈의 할 일과 손댈 파일 범위 안에서 구현한다. 범위 밖 변경이 필요하면 먼저 묻는다.
- 서로 독립인 작업 단위가 여럿이면 worker 서브에이전트에 나눠 맡길 수 있다. 같은 파일을 만지는 단위는 동시에 돌리지 않는다.
- 프로젝트에 있는 정적 검사와 테스트를 돌리고, 실패하면 고친 뒤 다시 돌린다.
- 커밋되는 문서는 머지 전에 이 브랜치에 넣는다. 넣을 문서는 `references/docs-update.md`에 있다.

### 5. 리뷰

opus 세션이면 `/review-code`로 브랜치 diff를 리뷰한다. sonnet 세션이면 Agent 도구에 model `opus`를 주고, `<이 스킬 폴더>/../review-code/SKILL.md` 절차대로 리뷰해 결과만 돌려 달라고 맡긴다. 나온 것은 같은 브랜치에서 고치거나 안 고친 까닭을 PR 본문에 적는다. 보안 감사 항목과 지시서 내용은 `references/pr-and-merge.md`에 있다.

### 6. PR과 CI

`references/pr-and-merge.md`대로 PR을 올리고 CI가 통과할 때까지 고친다. 행의 머지 전 확인 칸이 차 있으면 상태를 머지 전 확인으로 바꾸고, 일정 표에서 이 세션의 줄을 `<세션> PR #N 확인과 머지`로 고친다. 그런 다음 사용자가 확인할 내용과 PR 링크를 알린 뒤 worktree를 그대로 두고 멈춘다.

### 7. 머지

머지 전 확인 칸이 비어 있거나 사용자가 확인을 마쳤으면 `references/pr-and-merge.md`의 머지 절차를 따른다.

### 8. 마무리

`references/wrap-up.md`대로 worktree와 브랜치를 정리하고, 대기열 행을 배포 대기 표로 옮기고, `LOCAL-TRACK.md`에 확인 묶음을 만든다. 같은 배포 묶음의 세션이 모두 배포 대기 표에 있으면 `/deploy`로 배포할 차례라고 알린다.

## 완료 보고

첫 줄에 결과를 쓰고, 그 뒤에 PR 링크와 CI 결과, 리뷰에서 고친 것과 안 고친 것, 갱신한 문서, 대기열 행을 옮긴 곳, 확인 묶음 제목, 다음 세션과 여는 날짜를 적는다. 확인한 것만 완료로 적는다.

## 주의사항

- CI 결과를 확인한 뒤에 완료를 보고한다. 실패는 출력과 함께 보고한다.
- 이슈, PR, 커밋 메시지는 공개 텍스트다. 전역 보안 규칙을 따르고 운영 데이터와 개인 맥락을 넣지 않는다.
