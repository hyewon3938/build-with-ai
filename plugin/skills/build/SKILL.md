# /build - 기능 구현 스킬

`.claude/plans/`에 저장된 설계 계획서를 로드하고, 계획대로 정확히 구현한다.

## 입력

$ARGUMENTS

인자가 없으면 `.claude/plans/` 디렉토리에서 가장 최근 계획서를 자동으로 선택한다.

## 실행 흐름

### 1. 계획서 로드

```bash
ls -lt .claude/plans/*.md
```

인자가 있으면 해당 파일을, 없으면 최신 파일을 읽는다.
계획서가 없으면 "설계 계획서가 없습니다. /design을 먼저 실행해주세요." 출력 후 종료.

### 1-2. 완료 게이트 확인 + /goal 제안

계획서의 "완료 게이트 (DoD)" 섹션을 읽고:

1. 사용자에게 복사용 `/goal` 한 줄을 제안한다. `/goal`은 사용자 명령이라 직접 설정할 수 없다 — 제안만 하고 바로 진행한다 (설정 여부는 사용자 선택). `/design` 완료 안내에 따라 사용자가 이미 붙여넣었거나 입력해 둔 상태일 수 있으므로 "이미 붙여넣었다면 이 제안은 무시" 한 줄을 덧붙인다.
2. `/goal` 설정 여부와 무관하게 이 게이트는 9단계 완료 보고 전 **자기 점검 기준**이다 — 게이트 미충족 상태로 "완료"라고 보고하지 않는다.
3. 계획서에 완료 게이트 섹션이 없으면(구버전 계획서) 구현 상세·테스트 계획으로부터 즉석에서 게이트를 구성해 1을 수행한다.

### 2. 현재 상태 확인

```bash
git status
git branch --show-current
```

- 계획서에 명시된 브랜치에 있는지 확인
- 다른 브랜치에 있으면 올바른 브랜치로 전환
- 커밋되지 않은 변경이 있으면 사용자에게 알림

### 3. 구현

계획서의 "구현 상세" 섹션을 순서대로 실행한다:

- 각 작업 단위별로 코드를 작성
- 작업 단위가 많고 서로 독립적이면 worker 서브에이전트에 병렬 위임할 수 있다 — 지시서 4요소(목적·범위·반환 형식·금지 사항) 필수, 같은 파일을 만지는 단위는 동시 실행 금지
- **계획서에 없는 변경은 하지 않는다** (scope creep 방지)
- 계획서와 다른 방식이 더 나은 경우, 사용자에게 먼저 물어본다
- 프로젝트 컨벤션(`docs/conventions.md` 등)의 규칙을 준수한다

### 3-1. ADR 파일 생성 (계획서에 ADR 항목이 있으면)

계획서의 "ADR 작성" 섹션에 명시된 경우:

1. `docs/adr/template.md`를 복사해 `docs/adr/NNNN-<제목>.md` 생성
2. 계획서의 초안(Context/Decision/Alternatives/Consequences)을 그대로 옮기고, 실제 구현하며 발견된 세부사항을 보강
3. `docs/adr/README.md` 인덱스 테이블에 한 줄 추가 (번호, 제목, Status=Accepted, Date, Tags)
4. ADR 파일은 해당 기능 구현 커밋과 **같이** 커밋 (별도 커밋 금지 — 판단과 구현이 분리되면 의미가 약해짐)

**주의**: 프로젝트에 `docs/adr/` 디렉토리가 없고 계획서에도 ADR 항목이 없으면 이 단계를 건너뛴다.

### 3-2. 도메인 문서 본문 채우기 + 누락 검증 (해당 시)

프로젝트에 `docs/domains/<domain>.md`가 있고 이번 phase가 그 도메인 기능에 영향을 주면 **반드시 도메인 문서까지 갱신**한다. 코드만 머지되고 도메인 문서가 비어 있는 상황 방지가 목적.

#### 3-2-1. 영향 도메인 식별

이번 phase에서 변경한 파일 경로 → 매핑되는 도메인 문서:

```bash
git diff --name-only main...HEAD | grep -E 'src/(agents|cron|shared|domains)/' | head -20
```

매핑 규칙:
- `src/agents/<domain>/*` → `docs/domains/<domain>.md`
- `src/cron/<domain>-*.ts` → 관련 도메인 문서
- `db/migrations/<domain>-*.sql` → 관련 도메인 문서
- 매핑이 모호하면 사용자에게 확인

#### 3-2-2. 골격 vs 본문 점검

`/design` 단계에서 phase 섹션 골격(TODO 마커)이 작성되어 있는지 먼저 확인:

```bash
grep -n "TODO(\`/build\`)" docs/domains/<domain>.md
```

- **골격 있음** → TODO 마커 위치에 본문 채움 (마커 제거)
- **골격 없음** → `/design` 단계 누락. 본 단계에서 즉시 phase 섹션 추가 + 사용자에게 "`/design` 단계에서 도메인 문서 골격이 누락되어 본 단계에서 보충" 한 줄 보고

#### 3-2-3. 본문 작성 내용

다음 항목 중 phase 산출물에 해당하는 것을 작성 (해당 없으면 생략):
- **데이터 모델**: 신규/변경 테이블, 컬럼, 인덱스 (마이그레이션 번호 명시)
- **트리거/평가 로직**: polymorphic 구조나 평가 알고리즘이 있으면 표로 정리
- **fast path 명령어**: 신규 Slack 명령어 (정규식, 채널, 동작)
- **크론 시각**: 신규 cron 작업 (시각, 의도, 산출물)
- **흐름도**: ASCII 다이어그램 또는 단계 목록
- **다음 phase 연결**: 확장 가능성, 의존하는 후속 작업
- **결정 기록 link**: 관련 ADR

#### 3-2-4. 파일 구조 섹션 갱신 (해당 시)

도메인 문서 끝에 `파일 구조` 코드 블록이 있으면 신규 파일 경로를 추가한다.

#### 3-2-5. 커밋 포함

도메인 문서 갱신은 해당 phase 구현 커밋과 **같이** 커밋 (별도 커밋 금지 — 코드와 문서가 분리되면 머지 시 한쪽만 들어가는 사고 발생).

**주의**: 프로젝트에 `docs/domains/` 디렉토리가 없으면 이 단계 전체를 건너뛴다.

### 3-3. 폐기 처리 시 카탈로그 정리 (해당 시)

이번 phase가 **기존 기능/시스템을 제거**하거나 **deprecation을 적용**하는 경우 (예: cron 작업 삭제, 도메인 모듈 폐기, scheduled task 제거):

#### 3-3-1. 폐기 대상 식별

```bash
# 이번 PR에서 제거된 파일·디렉토리 목록
git diff --name-status main...HEAD | grep '^D' | head -20
git diff --name-status main...HEAD | grep '^R' | head -20  # 이름 변경된 것도 점검
```

#### 3-3-2. 카탈로그·도메인 문서 잔존 흔적 점검 (필수)

폐기 대상 파일/기능명·관련 키워드로 다음 문서를 grep해 잔존 흔적을 찾는다:

```bash
# 카탈로그 + 도메인 문서 전체 점검 (대상 키워드는 PR 별로 다름)
grep -rn '<폐기 대상 키워드>' docs/features.md docs/domains/ docs/design-notebook/ README.md
```

폐기 대상 키워드 예시:
- 제거한 파일명 (예: `dev-cron.ts`)
- 제거한 테이블명 (예: `dev_analyses`)
- 제거한 cron 시각·기능명 (예: "개발 리포트", "nightly-dev-report")
- 제거한 명령어 (예: `사주 시드 보기`)

#### 3-3-3. 잔존 흔적 제거

발견된 항목은 본 PR에 포함시켜 모두 제거한다:
- `docs/features.md`: 폐기 기능 카탈로그 항목, 크론 표 줄, fast path 명령어 줄
- `docs/domains/<domain>.md`: 폐기 모듈 설명, 파일 구조 항목
- `README.md`: 기능 소개 단락, 다이어그램 라벨
- `docs/design-notebook/*.md`: phase 섹션 본문은 보존(서사이므로) — 단, "현재 운영 중" 같은 단정 표현이 있으면 시점 표기 추가

#### 3-3-4. 커밋 포함

폐기 처리 정리는 폐기 구현 커밋과 **같이** 커밋. 별도 커밋 금지 — 코드만 머지되고 문서에 죽은 기능이 남으면 카탈로그 정확성이 즉시 깨진다.

**주의**: "기능 제거" PR이 아니라 단순 리팩토링·이름 변경이라면 3-3-2의 키워드 grep만 짧게 돌려 잔존 흔적 점검만 수행하고 본문 변경 없이 종료한다.

### 3-4. features.md 카탈로그 갱신 (신규 기능 시)

프로젝트에 `docs/features.md`가 있고 이번 phase가 **사용자가 인식할 새 능력**(기능·명령어·크론·화면·API)을 추가하면 카탈로그에 항목을 추가한다. 폐기 정리(3-3)와 대칭 — 제거만 반영하고 추가를 빠뜨리면 카탈로그가 조용히 뒤처진다 (2026-07 사주 리포트 통합 기능군이 features.md에 통째로 누락된 사례).

- 기존 표·섹션 형식을 유지하며 한 줄 설명 + 관련 이슈/ADR 링크 추가
- 기존 기능의 동작이 바뀐 경우 해당 항목 서술도 수정
- 내부 리팩토링·측정 교정만 있는 phase는 건너뛴다
- 구현 커밋과 **같이** 커밋 (별도 커밋 금지)

**주의**: `docs/features.md`가 없는 프로젝트는 건너뛴다.

### 4. 커밋

계획서의 "커밋 계획"에 따라 커밋한다:

- 커밋 메시지는 프로젝트의 커밋 컨벤션을 따른다
- 각 커밋은 논리적으로 하나의 단위

### 5. 코드 리뷰 (실제 파일 검증)

구현 완료 후 `/review-code` 스킬과 동일한 수준의 실제 코드 리뷰를 수행한다.
**체크리스트만 나열하는 것은 리뷰가 아니다.** 반드시 아래 절차를 실행한다:

> **내장 리뷰 하이브리드**: 환경에 내장 `/code-review` 스킬이 있으면 중규모 이상 PR에서 먼저 실행해(effort: medium 이상) fresh-context 리뷰를 받고, 그 발견을 5-5 결과에 통합한다. 대형·고위험 PR은 `/code-review ultra`(클라우드 멀티에이전트, 과금) 고려. 단 아래 5-3 보안 감사는 공개 repo 특화 항목이라 내장 리뷰와 무관하게 **항상 직접 수행**.

#### 5-1. 변경 범위 확인
```bash
git diff main...HEAD --stat
```
(base 브랜치가 main이 아니면 해당 브랜치 사용)

#### 5-2. 변경된 모든 파일을 Read 도구로 다시 읽는다
- 커밋한 코드를 다시 읽으면서 실제로 점검한다
- 파일을 읽지 않고 체크리스트만 작성하면 안 된다

#### 5-3. 보안 감사 (최우선)
| 점검 항목 | 심각도 |
|----------|--------|
| 크리덴셜 하드코딩 (API 키, 비밀번호, 토큰) | CRITICAL |
| 환경변수 파일이 커밋에 포함됨 | CRITICAL |
| SQL Injection 가능성 (raw query 사용) | HIGH |
| 외부 입력 미검증 | HIGH |
| 민감 정보 로그 출력 | MEDIUM |
| 에러 메시지에 내부 정보 노출 | LOW |

#### 5-4. 코드 품질 및 리팩토링 점검
프로젝트 컨벤션(`docs/conventions.md` 등)에 정의된 코드 품질 기준과 리팩토링 기준을 참조하여 점검한다.
컨벤션 파일이 없으면 일반적인 코드 품질 기준(타입 안전성, 단일 책임, 네이밍, 중복 등)으로 점검한다.

#### 5-5. 리뷰 결과 출력
```markdown
## 코드 리뷰 결과

### 보안 감사
- [PASS/FAIL] 항목: 결과

### 코드 품질
- [PASS/WARN] 항목: 설명

### 리팩토링 제안
1. [지금/나중에] [파일:라인] 제안 내용
```

#### 5-6. 문제 발견 시 수정 후 추가 커밋

### 6. 정적 검사 + 테스트 실행

테스트 전에 프로젝트에 설정된 정적 검사를 먼저 돌린다 (예: `tsc --noEmit`, eslint — 프로젝트에 있는 것만).

계획서의 "테스트 계획"에 따라 테스트를 실행한다.
프로젝트의 테스트 도구를 확인하여 적절한 명령을 실행한다:

```bash
# package.json의 test 스크립트 또는 프로젝트 테스트 도구 사용
# 예: npx vitest run, npm test, npx jest, pytest 등
```

테스트 실패 시 수정 후 커밋.

### 7. PR 생성

```bash
git push -u origin <브랜치명>
gh pr create --base <베이스브랜치> --title "<커밋 컨벤션 제목>" --body "..."
```

`--base`는 프로젝트 컨벤션(`docs/conventions.md`)의 브랜치 전략을 참조한다. GitHub의 default branch와 무관하게 컨벤션에 정의된 베이스(보통 `main`)를 명시적으로 지정한다.

PR 본문에 반드시 `Closes #N`을 포함하여 머지 시 이슈가 자동으로 닫히도록 한다.
**PR 제목·본문은 공개 텍스트** — 보안 규칙 준수 (민감 정보·개인 상황·구체 취약점 노출 금지).

PR 생성 직후 CI를 확인한다:

```bash
gh pr checks <N> --watch
```

실패 시 원인 수정 → 재푸시 → 재확인까지가 이 단계다. CI 결과를 보지 않고 완료 보고하지 않는다.

PR 본문 형식:
```markdown
## 관련 이슈
Closes #N

## 변경 내용
- 변경사항 1
- 변경사항 2

## 코드 리뷰 결과
- [x] 보안 감사 통과
- [x] 타입 안전성 확인
- [x] 컨벤션 점검 완료
- [x] 코드 품질 확인

## 테스트
- [x] 테스트 케이스 1
- [x] 테스트 케이스 2
```

### 8. 프로젝트 히스토리 업데이트 (마일스톤급일 때만)

프로젝트 히스토리 파일(`docs/project-history.md` 등)이 있으면 **마일스톤급 변화일 때만** 완료 기록을 추가한다.

**마일스톤급 판단 기준** (하나라도 해당):
- 새 도메인/기능 출시 (사용자에게 새로운 능력 제공)
- 아키텍처/인프라 전환 (배포 방식·DB·런타임 변화)
- 마스터 이슈의 phase 완료 (마스터 자체 완료가 아니어도 phase 마일스톤이면 OK)
- 외부 청중(포트폴리오·면접·README)에게 보여줄 만한 변화

**아니면 history.md를 건드리지 않는다** — 일상 작업·버그 수정·리팩토링은 PR + 커밋 메시지로 충분. 설계 판단은 ADR로.

계획서에 히스토리 기록 내용이 있으면 그대로 사용. 형식: `### YYYY-MM-DD: 제목 (#issue, PR #pr)`.

### 8-2. 마스터 단위 완료 처리 (해당 시)

이번 PR이 **마스터 이슈의 마지막 phase**이거나 **마스터 자체를 close**하는 경우:

#### design-notebook 완결 처리
- `docs/design-notebook/<master>.md` 마지막 phase 섹션에 "## 결과/회고" 추가 (계획서에 회고 항목이 있으면 사용)
- 마스터 전체 요약(어떤 phase들이 무엇을 달성했는지)을 상단에 한 단락으로

#### 마스터 메모리 정리 제안
마스터 작업 동안 누적된 MEMORY 엔트리들을 점검하고 사용자에게 정리 제안:

1. `~/.claude/projects/<project>/memory/` 에서 마스터와 관련된 메모리 파일 검색:
   - `project_<master>_*.md` 패턴
   - 마스터 이슈 번호를 본문에서 참조하는 파일
2. 각 메모리에 대해 분류:
   - **유지**: 마스터 단위 핵심 원칙(charter) — 다음 작업에서도 참조됨
   - **갱신**: 상태가 변한 메모리 (예: "진행 중" → "완료")
   - **폐기**: 임시 추적용 메모리 (SUPERSEDED 마커, 임시 결정 등)
3. 분류 결과를 사용자에게 보여주고 동의 받은 뒤 일괄 처리

> 마스터 close 없이 phase만 끝난 경우는 이 단계 건너뜀. phase 단위 마감은 design-notebook 섹션 누적까지만.

### 10. 머지 후 마무리 (사용자가 머지한 뒤)

머지는 사용자 결정 — 무인 자동 머지 금지. 머지가 확인되면 같은 세션(또는 후속 세션)에서 이어서:

1. **CI·배포 확인**: `gh pr checks` / `gh run list`로 main CI 통과 확인. 배포 파이프라인이 있으면 배포 워크플로우 성공까지 확인 — "될 것이다"로 보고하지 않고 확인한 것만 완료로 보고
2. **프로덕션 검증** (해당 시): DB 마이그레이션 적용, 신규 크론 슬롯 등록 등 배포 후에만 확인 가능한 항목
3. **계획서 아카이브**: 이번 계획서를 `.claude/plans/_archive/`로 이동. 라이브 디렉터리에 이슈가 이미 close된 다른 계획서가 남아 있으면 같이 이동 (휘발 정책 유지 — 아카이브 주체가 없으면 계획서가 수십 개씩 방치된다)
4. **project-history 재점검**: 8단계에서 "해당 없음"으로 판단했더라도 마일스톤급 여부를 한 번 더 확인 — 놓치면 다음 `/design`의 마스터 cross-check에서 회수

## 주의사항

- **계획서에 없는 코드를 작성하지 않는다.** 추가 변경이 필요하면 사용자에게 물어본다.
- 계획서의 Before/After 코드와 실제 코드가 다르면 (다른 PR에서 변경됨), 현재 코드 기준으로 판단하되 사용자에게 알린다.
- **코드 리뷰 단계에서 반드시 변경된 파일을 다시 읽어야 한다.** 체크리스트만 나열하는 건 리뷰가 아니다.
- 코드 리뷰에서 보안 이슈 발견 시 반드시 수정 후 진행.
- 커밋 3~5개가 쌓이면 PR 생성을 고려한다.
- **CI 확인 없이 "완료"라고 보고하지 않는다** — PR 생성 후·머지 후 모두. 실패는 출력과 함께 그대로 보고.
- 마일스톤·마스터 완료 판단은 **자동으로 건너뛰지 말 것** — 8/8-2 단계는 PR 작성 후 한 번 더 능동적으로 검토. 마스터 메모리 정리를 빠뜨리면 죽은 메모리가 누적된다.
- **도메인 문서 누락 방지** — 3-2 단계는 `docs/domains/` 디렉토리가 있는 프로젝트에서 절대 건너뛰지 말 것. 코드만 머지되고 도메인 문서가 비어 있으면 다음 phase에서 같은 작업이 반복됨 (2026-05-17 인사이트 v2 Phase 3 사례). `/design`에서 골격이 누락된 경우라도 본 단계에서 보충하고 사용자에게 보고.
- **폐기 흔적 잔존 방지** — 3-3 단계는 기능 제거/폐기 PR에서 절대 생략 금지. 코드는 제거됐는데 features.md·도메인 문서·README에 "운영 중"으로 남아 있으면 카탈로그가 거짓말을 한다 (2026-05-17 dev-report 폐기 작업에서 features.md 잔존 발견 사례). 폐기 키워드 grep을 한 번이라도 돌리는 게 핵심.
