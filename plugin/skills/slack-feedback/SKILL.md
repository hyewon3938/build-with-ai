# /slack-feedback - 슬랙 피드백 정리 스킬

슬랙에 게시한 호출 기록에 달린 피드백 가운데 처리 표시가 없는 행을 운영 DB에서 모두 가져온다. 행마다 원인을 확인하고, 같이 고칠 수 있는 행끼리 세션 하나로 묶어 세션마다 새 세션 카드를 띄운다. 카드는 사용자가 누를 때만 새 세션으로 시작하고, 이 스킬이 세션을 직접 시작하지는 않는다. 사용자가 카드로 시작하지 않은 세션은 다음 실행 1단계에서 대기열로 옮긴다.

지난번 보고 뒤에 들어온 행인지는 마지막으로 보고한 행 번호로 가리고, 이 번호를 워터마크라고 부른다. 보고했지만 아직 고치지 않은 행은 처리 표시가 없어서 다음 실행에 다시 모이므로, 대기열에 적어 두지 않아도 빠지지 않는다.

## 입력

$ARGUMENTS

- 비어 있으면 처리 표시가 없는 행을 모두 본다.
- 사용자가 먼저 고칠 문제를 말하면, 그 문제마다 세션을 따로 만들어 보고 맨 앞에 둔다. 나머지 행은 같이 고칠 수 있는 것끼리 묶는다.
- 행 번호를 받으면 그 번호 뒤의 행만 본다.

## 경로 규칙

메인 체크아웃은 `git worktree list --porcelain`의 첫 `worktree` 줄이다. `LOCAL-SESSIONS.md`, `LOCAL-TRACK.md`, 프로젝트 LOCAL 파일은 worktree 안에서 불렀어도 메인 체크아웃의 절대 경로로 읽고 고친다. 운영 DB 조회도 메인 체크아웃에서 돌린다.

메인 체크아웃이 옛 브랜치에 있을 수 있으므로, 원인을 찾으려고 코드를 읽을 때는 `git fetch` 뒤 `git worktree add --detach <스크래치패드>/main-ro origin/<base>`로 기본 브랜치 최신을 따로 체크아웃해 거기서 읽고, 보고를 마치면 `git worktree remove`로 지운다.

## 실행 흐름

### 1. 워터마크 읽기와 지난 카드 정리

메인 체크아웃 `LOCAL-SESSIONS.md` 「지금」의 피드백 보고 줄에서 워터마크와 지난번에 띄운 카드 제목을 읽는다. 줄이 없으면 옛 이름인 피드백 반영 줄을 읽는다.

지난 카드마다 `list_sessions`(`include_archived: true`)에서 같은 제목의 세션을 찾고, 세션 이름이 바뀌었을 수 있으니 그 세션이 만들었을 이슈와 브랜치도 `gh issue list`·`gh pr list --state all`로 본다. 시작한 흔적이 없는 카드는 그 카드의 시작 프롬프트를 대기열 행으로 옮긴다. 행 형식과 넣을 자리는 대기열 문서의 규칙을 따르고, 시작 프롬프트 원문은 세부 문서나 행의 메모 칸에 둔다. 옮긴 카드가 아직 남아 있으면 `dismiss_task`로 거둔다. 이번 실행에서 같은 원인의 새 행이 들어오면 옮긴 대기열 행에 합칠 행으로 적는다.

프로젝트 LOCAL 파일에서 슬랙 피드백을 가져오는 방법을 적은 절을 찾아 그 절만 읽는다. 피드백 표와 컬럼, 열린 행 조건, 메시지 표, 슬랙 채널, 처리 표시 명령, 교정 쌍 파일이 대상이다.

세션끼리 겹치는지 보려고 `LOCAL-SESSIONS.md`의 대기열에서 상태가 대기인 행의 이름과 손댈 파일, 마지막 배포 시각을 읽는다. `gh pr list --state open --json number,title,files`로 열린 PR이 고치는 파일도 본다. `LOCAL-TRACK.md`는 체크하지 않은 항목만 본다.

### 2. 행 가져오기

조회 스크립트는 `<이 스킬 폴더>/../../scripts/db-query.mjs`다. `realpath`로 심링크와 `..`를 푼 경로로 부르고, 결과 제한, 폴더 고정, 오류 처리는 `<이 스킬 폴더>/../track/references/checks.md`의 db 절을 따른다. 표와 컬럼 이름은 프로젝트 절에 적힌 것을 쓴다.

```bash
node <스크립트 절대 경로> --limit 200 <<'SQL'
SELECT id, character_id, call_id, trace_kind, source, kind, text, created_at
FROM call_feedback
WHERE removed_at IS NULL AND resolved_at IS NULL
ORDER BY id
SQL
```

워터마크보다 번호가 큰 행은 새 행, 작은 행은 지난 보고에 있던 행으로 나눠 둔다.

프로젝트 절에 유저가 메시지에 단 반응을 가져오는 조회가 적혀 있으면 반응 워터마크 뒤의 행을 함께 가져온다. 좋다는 반응만 달린 말풍선은 고칠 것이 없으니 수만 세고, 싫다는 반응은 아래 단계에서 피드백 행과 같은 방식으로 다룬다.

프로젝트 절에 운영자 검토 기록 표가 적혀 있으면 처리 표시가 없는 행을 모두 함께 가져온다. 운영자 검토 기록은 운영자가 보내기 전 문안에 누른 취소, 재생성, 승인을 한 번에 한 행씩 쌓은 기록이고, 같은 자리에서 이어진 행은 묶음 값으로 묶여 있다.

열린 행이 없으면 워터마크를 알리고 끝낸다. 조회 스크립트가 설정 오류로 끝나면 프로젝트 절에 적힌 목록 명령을 보여 주고 승인을 받아 돌리거나, Slack MCP 읽기 도구로 프로젝트 절의 채널을 본다.

행이 많으면 3~5단계를 서브에이전트에 나눠 맡긴다. 사용자가 먼저 고칠 문제로 말한 것은 문제마다 하나씩, 나머지는 한두 개에 맡기고, 지시서에는 기본 브랜치 체크아웃 경로, 조회 명령, 행 목록, 이 스킬의 3단계 확인 항목을 넣는다.

### 3. 원인 확인

- 같은 호출에 달린 행을 묶는다. 종류만 달린 행과 이유만 달린 행은 함께 읽는다.
- 호출이 가리키는 캐릭터 메시지를 메시지 표에서 찾고, 앞뒤 대화와 메시지 종류, 보낸 시각을 확인한다.
- 보낸 시각을 마지막 배포 시각과 `LOCAL-TRACK.md` 묶음 머리 줄의 배포 시각에 대조한다. 배포 전 메시지면 그 뒤에 배포한 작업이나 머지만 하고 배포하지 않은 작업이 이미 고쳤는지 먼저 본다.
- 같은 캐릭터의 같은 표현이나 같은 소재를 지적한 행이면, 처리 표시가 된 지난 피드백 행 가운데 같은 내용이 있는지 피드백 표에서 찾는다. 있으면 재발로 적고, 지난번에 고친 곳과 그 뒤 같은 표현이 다시 나온 메시지를 함께 적는다. 재발한 원인은 공통 문안 예시만 바꾸는 쪽으로 다시 묶지 않는다.
- 특정 캐릭터가 되풀이하는 표현이면, 그 표현을 끌어낸 캐릭터 데이터(진행 중인 일과 생성 때 정한 기억, 하루 각본의 블록)를 기억 표와 각본 표에서 찾고, 공통 문안의 예시가 그 표현을 허락하는 틀로 읽히는지도 함께 본다. 원인이 캐릭터 데이터에 있으면 운영 데이터 수정이 필요한 일로 적는다.
- 문제 문장과 결이 같은 프롬프트 문구나 코드를 찾아 파일:줄로 적는다. 원인을 확정하지 못하면 확정하지 못했다고 적고, 세션에서 그 턴의 프롬프트를 복원해 확인할 일로 넘긴다.
- 피드백이 고쳐 달라는 말 없이 동작을 묻는 질문이면 답을 찾아 보고에 적고, 답을 보니 고칠 것이 있으면 세션 묶기로 넘긴다.

### 4. 교정 쌍 쌓기

교정 쌍은 문제가 된 말풍선과 사용자가 대신 쓴 문장을 한 쌍으로 묶은 기록이다. 프로젝트 절에 교정 쌍 파일이 적혀 있으면, 새 행 가운데 사용자가 대신 쓸 문장을 적은 행을 골라 그 파일 끝에 붙인다. 더 짧게, 덜 가볍게처럼 방향만 적은 행은 넣지 않고, 프로젝트 절에 파일이 없으면 이 단계를 건너뛴다.

- 원래 문장은 3단계에서 찾은 메시지에서 문제가 된 말풍선만 옮긴다. 호출 기록의 출력과 실제로 보낸 문장이 다르면 보낸 문장을 쓴다.
- 고친 문장과 이유는 피드백 원문에서 그대로 옮긴다.
- 피드백 행 번호, 메시지 id, 장면 한 줄, 3단계에서 찾은 규칙 파일:줄을 함께 적는다. 항목 형식과 문제 종류를 적는 태그는 파일 머리에 적힌 것을 따른다.

교정 쌍은 규칙 문장을 고칠 때 같은 종류의 사례가 몇 개인지 세는 근거와, 규칙을 고친 뒤 전후를 비교하는 예시로 쓴다. 모델은 프롬프트에 들어간 예시 문장을 그대로 따라 쓰기 때문에, 프롬프트로 옮길 때는 문제의 종류만 가져와 규칙 문장으로 고쳐 쓴다.

피드백은 대개 하지 말라는 말로 오지만, 규칙 문장은 그 자리에서 대신 할 모양을 먼저 적는다. 모델은 하지 말라는 줄보다 해야 할 모양을 더 잘 따르고, 금지어를 그대로 적으면 그 말을 오히려 떠올려 쓰기도 한다. 그래서 세션 시작 프롬프트에 피드백마다 바라는 모양 한 줄을 적고, 금지는 그 모양만으로 막히지 않을 때 이유와 함께 짧게 덧붙인다. 특정 단어나 표현을 꼭 막아야 하면 프롬프트에 단어 목록을 늘리기보다 보내기 전 코드 검사로 막을 수 있는지 먼저 본다. 바라는 모양을 보여 줄 예시를 넣을 때는 교정 쌍 문장을 그대로 옮기지 않고, 장면이 다른 예시를 2개 이상 새로 써서 결만 따라 하게 한다.

### 5. 운영자 검토 기록 해석

2단계에서 가져온 운영자 검토 기록을 묶음 값으로 묶고, 묶음마다 취소하거나 재생성한 문안과 마지막에 승인한 문안을 나란히 놓는다. 취소와 재생성은 그 문안이 별로였다는 신호로, 승인은 다시 만든 문안이 나아졌다는 신호로 읽는다. 다만 운영자는 재생성을 끝없이 누를 수 없어 나쁘지 않은 정도에서 승인하기도 하므로, 승인한 문안을 잘 쓴 예시로 단정하지 않는다.

- 묶음마다 취소한 문안이 무엇이 별로였는지 짐작해 한 줄로 적고, 승인한 문안에서 그 점이 나아졌는지, 승인한 문안에도 남은 문제가 있는지 적는다.
- 같은 종류의 문제가 여러 묶음에 보이면 3단계처럼 결이 같은 프롬프트 문구나 코드를 찾아 파일:줄로 적는다.
- 짐작한 해석은 보고에 묶음마다 적어 사용자에게 맞는지 확인받는다. 확인받기 전에는 세션에 넣지 않고 처리 표시도 하지 않는다. 사용자가 이유를 직접 적어 주면 4단계 교정 쌍 기준에 맞는 행은 교정 쌍으로도 쌓는다.

### 6. 세션으로 묶기

호출마다 묶은 행을 먼저 아래 가운데 하나로 정한다.

- 좋음만: 좋았다는 표시만 있어 고칠 것이 없다.
- 이미 고침: 배포했거나 머지한 작업이 원인을 고쳤다.
- 질문: 동작을 물은 행이고, 답만 드리면 된다.
- 고칠 것: 원인을 고치는 세션이 필요하다.

고칠 것은 세션으로 묶는다.

- 사용자가 먼저 고칠 문제로 말한 것은 문제마다 세션 하나로 따로 둔다. 같은 원인의 다른 행이 있으면 그 세션에 함께 넣는다.
- 나머지는 같은 파일을 고치거나 같은 원인에서 나온 행끼리 세션 하나로 묶는다. 세션 하나는 이슈 1개와 PR 1개로 끝낼 수 있는 크기로 두고, 크면 나눈다.
- 대기 중인 대기열 세션이나 열린 PR과 손댈 파일, 원인이 겹치면 보고에 그 이름을 적고, 그 세션에 합쳐 열지 따로 열지 사용자가 정하게 한다. 대기열 행은 고치지 않는다.
- 같은 파일을 고치는 세션 두 개는 동시에 열 수 없다고 적고, 여는 순서를 제안한다.
- 원인을 고치는 방법에 사용자만 정할 수 있는 판단(캐릭터의 말과 행동, 비용, 운영 데이터 수정)이 남으면 그 판단을 보고에 질문으로 올린다. 설계가 크면 `/design <주제>`로 먼저 설계하자고 제안한다.

프로젝트 절에 적용 범위를 나누는 기준이 있으면, 세션마다 모든 캐릭터에 공통으로 적용할 규칙으로 고칠지 그 캐릭터 설정으로 고칠지도 그 기준으로 정한다.

### 7. 시작 프롬프트 쓰기

세션마다 새 세션이 받을 시작 프롬프트를 쓴다. 새 세션은 이 대화를 볼 수 없으므로 프롬프트만 읽고 일할 수 있게 쓴다.

- 첫 줄은 `/build <세션이 할 일 한 문장>`이다.
- 피드백 원문 요지와 행 번호, 메시지 id, 확인한 원인과 근거 파일:줄, 손댈 파일, 바라는 모양, 세션에서 정할 것, 사용자가 이미 정한 것을 적는다.
- 프로젝트 절에 코드와 함께 고쳐야 하는 외부 지시서가 적혀 있고 세션이 그 파일을 고치면 그 사실을 적는다.
- 끝에 머지한 뒤 처리 표시할 행 번호와 프로젝트 절의 처리 표시 명령을 적는다. 운영자 검토 기록 묶음이 들어 있으면 그 표시 명령도 적는다.

### 8. 카드 띄우기

세션마다 `start_session`을 `initiation: "own_initiative"`, `context: "fresh"`, `use_worktree: true`로 불러 카드를 띄운다. `prompt`에는 7단계의 시작 프롬프트를, `background`에는 피드백 정리에서 나온 세션이라는 것과 사용자가 이미 정한 것을 적는다. 사용자가 먼저 고칠 문제로 말한 세션부터 띄우고, 같은 파일을 고쳐 동시에 열 수 없는 세션은 카드 제목이나 프롬프트 첫머리에 먼저 열 세션 이름을 적는다. 카드가 거부되면 그 세션의 시작 프롬프트를 보고에 코드 블록으로 적고 다음 실행에 대기열로 옮길 대상에 넣는다.

카드는 일주일 뒤 사라지므로, 사용자가 일주일 안에 다시 실행하지 않아도 남은 카드는 1단계의 기준으로 대기열에 옮긴다.

### 9. 워터마크 갱신

「지금」의 피드백 보고 줄을 이번에 본 마지막 행 번호와 그 행이 들어온 시각, 이번에 띄운 카드 제목으로 고친다. 옛 이름의 피드백 반영 줄이 있으면 이 줄로 바꾼다. 줄 형식은 아래와 같다.

`- **피드백 보고.** 슬랙 피드백 행 #<번호>(<M/D HH:MM>)와 반응 #<번호>까지 <M/D>에 세션 카드로 보고했다. 카드: <제목>, <제목>. 카드로 시작하지 않은 세션은 다음 /slack-feedback 실행 때 대기열로 옮긴다. 처리 표시가 없는 행은 다음 실행에 다시 모인다.`

확인 목록에 같은 문제를 보는 체크하지 않은 항목이 있으면 그 묶음의 확인 결과에 `<M/D>:`로 시작하는 줄로 사례를 적는다. 항목 체크와 닫는 기준 판단은 `/track`에서 한다.

### 10. 처리 표시

프로젝트 절의 처리 표시 명령으로 좋음만과 이미 고침 행을 결과 종류와 이슈 번호별로 표시한다. 처리 표시는 운영 DB에 쓰고 슬랙 원글에 리액션을 다는 명령이지만, 사용자가 이 스킬이 정한 이 두 종류의 행은 승인 없이 표시하라고 정해 두었으므로 묻지 않고 바로 실행한다. 질문 행은 답을 드린 뒤 사용자가 맞다고 하면 wontfix로 표시하고, 사용자가 고치지 않기로 한 행도 그 말을 들은 뒤 wontfix로 표시한다. 세션에 넣은 행은 그 세션이 머지한 뒤 시작 프롬프트에 적힌 명령으로 표시한다.

## 완료 보고

첫 줄에 열린 행 수와 그 가운데 새 행 수, 새 워터마크, 띄운 카드 수를 쓴다. 1단계에서 대기열로 옮긴 지난 카드가 있으면 그다음 줄에 적는다. 그 뒤에 아래 순서로 쓴다.

1. 카드로 띄운 세션. 세션마다 이름, 원인 요약, 포함 행, 정할 것을 두세 줄로 적는다. 시작 프롬프트는 카드에 들어 있으므로 채팅에 다시 적지 않는다.
2. 겹치는 대기열 세션이나 열린 PR, 같이 열 수 없는 세션과 여는 순서 제안.
3. 질문 행의 답, 운영자 검토 기록 묶음별 해석, 고칠 것이 없는 행과 처리 표시한 행, 새로 쌓은 교정 쌍 수.
4. 사용자가 정해야 하는 판단. 하나씩 질문으로 묻는다.

## 주의사항

- 이번 실행에서 만든 세션은 카드로만 띄우고 대기열 표와 세부 문서에 넣지 않는다. 대기열에 넣는 것은 1단계에서 지난 카드 가운데 시작하지 않은 세션을 옮길 때뿐이다. 사용자가 세션을 바로 시작하라고 하면 그때 `initiation: "user_asked"`로 시작한다.
- 운영 DB는 읽기 전용 조회 스크립트로만 본다. 운영에 쓰는 명령 가운데 승인 없이 돌리는 것은 10단계의 좋음만·이미 고침 처리 표시뿐이고, 그 밖의 명령은 명령과 영향 범위를 알리고 승인을 받는다.
- 피드백 원문, 메시지 문장, 호출 번호, 캐릭터와 인물 이름은 채팅 보고와 LOCAL 파일에만 적는다. 이슈, PR, 커밋 메시지 같은 공개 텍스트에는 옮기지 않고, 시작 프롬프트에도 이슈와 PR에는 옮기지 말라고 적는다.
- Slack MCP는 읽기 도구만 쓴다. 메시지를 보내거나 리액션을 다는 도구는 쓰지 않는다.
