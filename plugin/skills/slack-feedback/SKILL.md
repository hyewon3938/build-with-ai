# /slack-feedback - 슬랙 피드백 반영 스킬

슬랙에 게시한 호출 기록에 달린 피드백 가운데 지난번 반영 뒤에 들어온 행을 운영 DB에서 가져온다. 원인이 같은 행을 묶어 대기 중인 세션이나 남은 작업에 합칠 수 있으면 합치고, 합칠 곳이 없으면 새 세션을 만든다. 어디까지 반영했는지는 마지막으로 반영한 행 번호로 남기고, 이 번호를 워터마크라고 부른다.

## 입력

$ARGUMENTS

- 비어 있으면 워터마크 뒤의 행을 모두 본다.
- 행 번호를 받으면 그 번호 뒤의 행부터 본다.

## 경로 규칙

메인 체크아웃은 `git worktree list --porcelain`의 첫 `worktree` 줄이다. `LOCAL-SESSIONS.md`, `LOCAL-TRACK.md`, 프로젝트 LOCAL 파일, 세션 세부 문서는 worktree 안에서 불렀어도 메인 체크아웃의 절대 경로로 읽고 고친다. 운영 DB 조회도 메인 체크아웃에서 돌린다.

## 실행 흐름

### 1. 워터마크와 합칠 곳 읽기

메인 체크아웃 `LOCAL-SESSIONS.md` 「지금」의 피드백 반영 줄에서 워터마크를 읽는다. 줄이 없고 입력에 행 번호도 없으면 어느 행부터 볼지 사용자에게 묻는다.

프로젝트 LOCAL 파일에서 슬랙 피드백을 가져오는 방법을 적은 절을 찾아 그 절만 읽는다. 피드백 표와 컬럼, 열린 행 조건, 메시지 표, 슬랙 채널, 처리 표시 명령이 대상이다.

합칠 곳을 찾으려고 `LOCAL-SESSIONS.md`의 「지금」, 「남은 작업」, 배포 대기 표, 대기열을 읽고, 대기열이 가리키는 세션 세부 문서는 소개와 목차를 읽는다. `LOCAL-TRACK.md`는 체크하지 않은 항목만 본다.

### 2. 새 행 가져오기

조회 스크립트는 `<이 스킬 폴더>/../../scripts/db-query.mjs`다. `realpath`로 심링크와 `..`를 푼 경로로 부르고, 결과 제한과 오류 처리는 `<이 스킬 폴더>/../track/references/checks.md`의 db 절을 따른다. 표와 컬럼 이름은 프로젝트 절에 적힌 것을 쓴다.

```bash
node <스크립트 절대 경로> --limit 100 <<'SQL'
SELECT id, call_id, trace_kind, source, kind, text, created_at
FROM call_feedback
WHERE removed_at IS NULL AND resolved_at IS NULL AND id > <워터마크>
ORDER BY id
SQL
```

새 행이 없으면 워터마크를 알리고 끝낸다. 조회 스크립트가 설정 오류로 끝나면 프로젝트 절에 적힌 목록 명령을 보여 주고 승인을 받아 돌리거나, Slack MCP 읽기 도구로 프로젝트 절의 채널을 본다.

### 3. 원인 확인

- 같은 호출에 달린 행을 묶는다. 종류만 달린 행과 이유만 달린 행은 함께 읽는다.
- 호출이 가리키는 캐릭터 메시지를 메시지 표에서 찾고, 앞뒤 대화와 메시지 종류, 보낸 시각을 확인한다.
- 보낸 시각을 `LOCAL-SESSIONS.md`의 마지막 배포 시각과 `LOCAL-TRACK.md` 묶음 머리 줄의 배포 시각에 대조한다. 배포 전 메시지면 그 뒤에 배포한 작업이 이미 고쳤는지 먼저 본다.
- 문제 문장과 결이 같은 프롬프트 문구나 코드를 찾아 파일:줄로 적는다. 원인을 확정하지 못하면 확정하지 못했다고 적고, 세션에서 그 턴의 프롬프트를 복원해 확인할 일로 넘긴다.

### 4. 행 나누기

호출마다 묶은 행을 아래 가운데 하나로 정한다.

- 좋음만: 좋았다는 표시만 있어 고칠 것이 없다.
- 이미 고침: 배포 전 메시지이고, 그 뒤 배포한 작업이 원인을 고쳤다.
- 대기 세션에 합침: 대기열 세션의 할 일이나 손댈 파일이 같은 원인을 다룬다.
- 남은 작업에 합침: 「남은 작업」에 같은 원인의 항목이 있다.
- 새 세션: 합칠 곳이 없다. 원인이 같은 행끼리 세션 하나로 묶는다.

`LOCAL-TRACK.md`에 같은 문제를 보는 체크하지 않은 항목이 있으면, 위 분류와 따로 그 항목의 사례로도 적는다.

### 5. 문서에 반영

- 대기열: 새 세션 행은 `<이 스킬 폴더>/../design/references/queue.md` 「순서」의 4가지로 작업할 순서에 맞는 자리에 끼워 넣고, 표 끝에 그냥 붙이지 않는다. 기존 대기 행보다 먼저 열 세션이면 그 행 위에 넣고, 넣은 뒤 맨 위 대기 행이 다음에 열 세션인지 확인하고 순서 번호를 다시 매긴다. 여는 날짜, 모델, 배포 묶음은 제안으로 적고, 여는 날짜가 정해져 있으면 일정 표에도 그 날짜로 줄을 넣는다. 대기 세션에 합친 행은 그 세션의 할 일 칸에 붙인다.
- 세부 문서: 대기열이 가리키는 세션 세부 문서에 이번 묶음 절을 만든다. 이 절은 세션이 머지되면 `/build` 마무리가 지운다. 행 번호 범위, 세션마다 피드백과 메시지 id, 원인과 고칠 파일:줄, 피드백으로 정해진 것, 세션에서 정할 것, 다른 곳에 합친 행, 처리 표시 제안을 적는다. 캐릭터 설정이나 관계 단계처럼 설계 원본 문서가 있는 결정을 바꾸는 세션이면 원본 문서와 절을 함께 적고, 원본을 먼저 고치도록 한다.
- 남은 작업: 합친 행은 항목의 사례 수와 메시지 id를 지금 상태로 고치고, 날짜별 경위를 항목 끝에 이어 붙이지 않는다. 사례가 쌓여 세션으로 나누면 `<이 스킬 폴더>/../design/references/queue.md` 「지금과 남은 작업 정리」대로 항목을 지운다. 새 세션은 대기열 행만 만들고 남은 작업에 가리키는 항목을 따로 넣지 않는다.
- 확인 목록: 해당 묶음의 확인 결과에 `<M/D>:`로 시작하는 줄로 사례를 적는다. 항목 체크와 닫는 기준 판단은 `/track`에서 한다.
- 프로젝트 절에 코드와 함께 고쳐야 하는 외부 지시서가 적혀 있고 새 세션이 그 파일을 고치면, 세션 행과 세부 문서에 그 사실을 적는다.

### 6. 워터마크 갱신

「지금」의 피드백 반영 줄을 이번에 반영한 마지막 행 번호와 그 행이 들어온 시각으로 고친다. 줄이 없으면 아래 형식으로 만든다.

`- **피드백 반영.** 슬랙 피드백 행 #<번호>(<M/D HH:MM>)까지 대기열과 <세부 문서 경로>에 반영했다.`

사용자가 일부 행을 다음으로 미루자고 하면 워터마크는 미룬 첫 행 앞 번호로 둔다.

### 7. 처리 표시 제안

프로젝트 절의 처리 표시 명령으로 좋음만과 이미 고침 행을 표시하는 명령을 결과 종류와 이슈 번호별로 만들어 보여 준다. 처리 표시는 운영 DB에 쓰고 슬랙 원글에 리액션을 달아서, 사용자가 승인한 명령만 실행한다. 세션이나 남은 작업에 합친 행은 그 작업을 머지한 뒤 그 이슈 번호로 표시한다.

## 완료 보고

첫 줄에 새 행 수와 새 워터마크를 쓴다. 그 뒤에 합친 곳, 새로 만든 세션과 제안한 여는 날짜·모델·배포 묶음, 확인 목록에 적은 사례, 승인이 필요한 처리 표시 명령을 적는다.

## 주의사항

- 운영 DB는 읽기 전용 조회 스크립트로만 본다. 처리 표시처럼 운영에 쓰는 명령은 명령과 영향 범위를 알리고 승인을 받는다.
- 피드백 원문, 메시지 문장, 호출 번호, 캐릭터와 인물 이름은 LOCAL 파일에만 적는다. 이슈, PR, 커밋 메시지 같은 공개 텍스트에는 옮기지 않는다.
- Slack MCP는 읽기 도구만 쓴다. 메시지를 보내거나 리액션을 다는 도구는 쓰지 않는다.
- 세션을 여는 날짜, 모델, 배포 묶음은 사용자가 정한다. 문서에는 제안으로 적고 완료 보고에서 확인을 받는다.
- 원인을 고치는 방법에 설계 판단이 필요하면 세부 문서의 세션에서 정할 것에 적고, 코드 수정은 세션에 맡긴다. 그 판단이 캐릭터의 말과 행동, 비용, 운영 데이터 수정처럼 사용자가 정해야 하는 일이면 `<이 스킬 폴더>/../design/references/queue.md` 「남은 작업에 넣는 기준」의 2번대로 완료 보고에서 정할 것을 알리고 설계하자고 제안한다.
