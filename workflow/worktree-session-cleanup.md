# worktree 세션의 머지 뒤 정리

> worktree 안에서 도는 세션이 머지 뒤 정리를 사용자에게 넘기면, 세션이 끝난 뒤 그 명령을 챙길 주체가 없어서 worktree가 하나씩 남는다. 막힌 원인이 세션의 위치에 있으면 worktree를 먼저 나오도록 순서를 바꾸고, 사람이 다시 요청해서 풀린 방법이 있으면 그 방법을 절차에 적는다.

## 9/14~9/16 세션 3개의 정리 기록

`/build` 스킬은 이슈 하나를 worktree 하나에서 구현하고, PR을 머지한 뒤 worktree와 브랜치를 지우는 데까지 한 세션에서 끝내게 되어 있다. Claude Code에서는 EnterWorktree로 세션을 worktree로 옮기고 ExitWorktree로 메인 체크아웃에 되돌리는데, 이 세션들이 돌던 권한 설정에서는 worktree 안에 있는 세션이 `git -C <메인 체크아웃>`으로 메인 체크아웃을 가리키거나 메인 체크아웃의 파일을 고치려 하면 Claude Code가 권한 확인 단계에서 그 명령을 거부했다.

9/14 random-ai-companion에서 PR을 머지한 세션은 마무리 절차의 첫 명령인 `git -C <메인 체크아웃> pull --ff-only`에서 거부됐고, 배포 뒤 확인 목록 파일을 고치는 편집도 같은 이유로 거부됐다. 세션은 남은 명령과 목록에 붙일 항목을 사용자가 직접 할 일로 정리해 보고하고 멈췄는데, 17:42에 사용자가 끝까지 하라고 다시 요청하자 ExitWorktree로 worktree를 남긴 채 나왔다. 메인 체크아웃에서는 같은 명령이 거부되지 않아서 세션은 worktree와 브랜치 정리를 모두 마쳤다.

같은 날 18:10에는 작업 방식을 손보던 다른 세션이 마무리 절차에 새 단계를 더해, worktree 안에서 시작한 세션이거나 `git -C` 명령이 권한 확인에서 거부되면 남은 명령을 완료 보고에 적고 사용자가 세션을 종료한 뒤 지우게 했다. 그 세션은 막혔을 때 사용자에게 넘기는 결말을 절차에 적었고, 30분쯤 앞서 다른 세션이 worktree를 나와 정리를 끝낸 방법은 절차에 넣지 않았다.

다음 날인 9/15에 PR을 머지한 세션은 같은 거부를 만나자 새 단계대로 pull, 잠금 해제, worktree 삭제, 브랜치 삭제 명령 4줄을 완료 보고에 적고 끝냈고, 그 worktree는 잠긴 채 다음 날까지 남았다.

9/16 세션은 시작할 때 전날 worktree가 남아 있는 것을 보고도 이번 작업과 겹치는 변경이 없는지만 확인하고 구현을 시작했다. 머지 뒤에는 같은 `-C` 거부를 만났고 반복문으로 묶은 git 명령도 거부돼서, 다시 명령을 넘기며 전날 worktree도 남아 있다고 보고했다. 사용자가 남은 worktree까지 지우고 앞으로는 정리를 끝까지 하라고 요청한 뒤에야 세션은 worktree 2개와 브랜치 2개를 지우고 마무리 절차를 고쳤다.

## 정리가 막힌 원인

이전 절차는 1단계에서 `git -C <메인 체크아웃> pull --ff-only`로 base 브랜치를 맞추고, 2단계에서 ExitWorktree로 worktree를 남긴 채 나온 뒤, 3단계에서 `git -C <메인 체크아웃>`으로 worktree와 브랜치를 지웠다. worktree를 나오는 단계는 2단계에 있는데 첫 명령부터 worktree 안에서 메인 체크아웃을 가리키니, 세션은 1단계에서 거부되고 나오는 단계까지 가지 못했다.

Claude Code가 거부한 것은 worktree 안에서 메인 체크아웃을 가리키는 명령이었고, 같은 명령을 메인 체크아웃에서 치면 거부될 이유가 없다. 막힌 원인은 명령 내용보다 세션이 있는 위치와 단계 순서에 있었는데, 9/14에 절차를 고친 세션은 이 순서를 그대로 두고 거부를 만났을 때의 결말만 더했다.

## 바꾼 정리 순서

고친 [마무리 절차](../plugin/skills/build/references/wrap-up.md)에서는 세션이 worktree를 먼저 나온 뒤 메인 체크아웃에서 `-C` 없이 나머지를 한다.

1. ExitWorktree에 `remove`를 줘서 세션을 메인 체크아웃으로 되돌리면서 worktree도 지운다. 브랜치에 커밋이 남아 있으면 ExitWorktree가 거부하므로, 브랜치 끝 커밋이 원격 base 브랜치에 들어갔는지 `git branch --contains <커밋> -r`로 확인한다. `origin/<base>`가 나오면 잃는 작업이 없다고 한 줄 알린 뒤 `discard_changes: true`로 다시 부르고, 나오지 않으면 멈추고 사용자에게 묻는다.
2. 메인 체크아웃에서 `git pull --ff-only`로 base 브랜치를 맞추고 `git worktree remove`와 `git branch -d`로 남은 것을 지운다. ExitWorktree는 자기가 만든 이름의 브랜치만 지워서, 프로젝트 규칙대로 이름을 바꾼 브랜치는 이 단계에서 지운다. squash로 머지해 `-d`가 거부하면 PR이 머지 상태인지 확인하고 `-D`로 지운다.
3. 앞 세션이 남긴 worktree도 함께 지운다. 브랜치가 `git branch --merged origin/<base>`에 나오고 잠금이 없으면 지우고, Claude Code 세션이 잠가 둔 worktree는 그 세션이 아직 쓰고 있을 수 있어서 보고만 한다.
4. `git worktree list`, `git branch --list`, `git ls-remote --heads origin`으로 로컬과 원격에 남은 것이 없는지 확인한다.
5. worktree를 나올 수 없을 때만 남은 명령을 완료 보고에 적어 사용자에게 넘긴다.

세션이 직접 지우는 범위를 넓혔으니, 되돌릴 수 없는 삭제마다 근거를 먼저 확인하게 했다. 커밋을 버리기 전에는 원격 base 브랜치에 그 커밋이 있는지를, 앞 세션의 worktree를 지우기 전에는 머지 여부와 잠금을 본다. 어느 쪽이든 명령 하나로 판정이 나서 세션이 그 자리에서 정할 수 있고, 판정이 안 나는 경우에만 사용자에게 묻는다.

## AI 세션에서 더 자주 생기는 이유

사람이 자기 할 일을 메모해 두면 그 사람이 나중에 다시 보는데, 세션이 완료 보고에 적은 명령은 사용자가 그 보고를 다시 찾아 읽어야 실행할 수 있다. 다음 세션은 앞 세션의 보고를 읽지 않고 시작 전 확인 항목만 보기 때문에, 9/16 세션도 남은 worktree가 이번 작업과 겹치지 않는 것만 확인하고 지나갔다.

세션은 권한 확인에 거부되면 그 거부를 지켜야 할 제한으로 다루고, 순서를 바꾸면 풀리는지 따져 보기 전에 사용자에게 넘기는 쪽을 고른다. 제한을 지키는 판단 자체는 맞는데, 같은 명령을 허용되는 위치에서 치는 방법까지 함께 포기하게 된다. 9/14 세션도 사용자가 다시 요청한 뒤에야 worktree를 나오는 방법을 썼다.

막힌 사례를 절차에 반영하는 세션은 실패 보고를 읽고 절차를 고치는데, 실패 보고에서 가장 먼저 보이는 것이 막혔다는 사실이라 막혔을 때의 결말을 적기 쉽다. 사람이 다시 요청해서 풀린 방법은 그 세션의 대화 기록에만 있어서, 누군가 따로 찾아 옮기지 않으면 절차에 반영되지 않는다.

## 일반화

- 권한 확인에 막힌 단계는 사용자에게 넘기기 전에 순서를 바꿔서 풀리는지 먼저 본다. 거부 사유가 명령을 친 위치에 있으면 그 위치를 벗어나는 단계를 앞으로 옮긴다.
- 세션이 끝나면 넘긴 명령을 챙길 주체가 없으니, 사용자에게 넘기는 결말은 마지막 수단으로만 둔다.
- 사람이 다시 요청해서 풀린 막힘은 풀린 방법까지 절차에 적어야 다음 세션이 같은 단계에서 멈추지 않는다.
- 머지 여부와 원격 반영처럼 명령 하나로 판정되는 정리는 세션이 끝내고, 며칠 실제 동작을 봐야 판정되는 확인만 사람에게 남긴다. [세션 지시서와 확인 장부 가르기](instruction-sheet-vs-watch-ledger.md)에서 장부 정리를 사람만 시작하게 한 것과 같은 기준이다.
- 되돌릴 수 없는 삭제는 잃는 것이 없다는 근거를 명령으로 확인한 뒤 하고, 근거가 안 나오면 묻는다.
- 앞 세션이 남긴 것도 정리 범위에 넣되, 다른 세션이 쓰고 있을 수 있는 것은 보고만 한다.

## 메타

이 글을 메타 repo에 둔 것은 다루는 문제가 random-ai-companion의 git 명령보다 격리된 세션이 권한 확인에 막혔을 때 맡은 일을 어디까지 끝내느냐에 가깝기 때문이다. 세션이 권한 확인에 막히는 곳은 worktree 정리 말고도 있어서, 순서를 바꿔 풀리는지 먼저 보고 넘기기는 마지막에 두는 기준을 다른 절차에도 그대로 쓸 수 있다.

9/16 random-ai-companion에서 마무리 절차를 위 순서로 고치고, 같은 자리에서 전날 남은 worktree와 그 세션의 worktree, 브랜치 2개를 지워서 `git worktree list`에는 메인 체크아웃만 남았다. 9/14부터 3일 동안 세션 3개가 같은 단계에서 정리를 사용자에게 넘겼고, 9/15 세션이 넘긴 worktree는 다음 날 사용자가 지워 달라고 할 때까지 남아 있었다.
