# 문서 상태 줄과 기능 색인

> 문서마다 맨 위에 지금 원본인지 기록인지를 한 줄로 적고, 색인은 그 줄에서 만든다. 기능을 고칠 때 볼 곳은 기능 색인 한 문서에 모으고, 문서가 가리키는 경로와 이름이 실제로 있는지는 커밋 훅이 검사한다.

## 문서가 늘면서 생긴 문제

설계 문서를 코드와 같은 repo에 두고 주제마다 하나씩 쓰다 보니 `docs/` 바로 아래 md가 50개 가까이 됐다. 끝난 작업의 계획서와 점검 기록이 지금 코드의 설계 원본과 같은 폴더에 섞여 있었고, 지난 버전에 쓰다가 다음 버전에서 일부 절만 코드에서 뺀 문서는 어느 절이 아직 맞는지 끝까지 읽어야 알 수 있었다. AI가 기능을 찾으려고 문서를 검색하면 지난 문서의 설명도 같이 나와서, 이미 없어진 동작을 지금 동작으로 읽고 판단하는 일이 생겼다.

문서에 적은 코드 경로도 코드가 바뀌는 속도를 따라가지 못했다. 파일을 지우거나 옮긴 뒤에도 문서에는 옛 경로가 남았고, `파일:줄 번호`로 적은 참조는 그 파일에 줄이 늘 때마다 다른 곳을 가리켰다. 설계 문서를 코드에 맞춰 한 번 손으로 고쳤는데도, 며칠 뒤에 세어 보니 없는 파일을 가리키는 경로가 현행 문서에 22곳 남아 있었다.

기능을 찾을 때 가장 먼저 여는 문서로는 머지할 때마다 한 줄씩 붙이는 변경 기록이 쓰이고 있었다. 주제별로 줄을 붙여 온 기록이라 같은 기능의 줄이 여러 곳에 흩어져 있었고, 뒤에 붙은 줄이 앞의 줄을 뒤집어도 앞의 줄은 그대로 남아 있었다. 세 문제는 모두 문서를 열어 읽기 전에는 그 문서를 근거로 써도 되는지 알 수 없어서 생겼다.

## 문서마다 적는 상태 줄

`docs/` 바로 아래 문서는 제목 바로 아래에 상태 줄 하나를 적는다. 값은 현행, 일부만 현행, 기록 세 가지이고, 일부만 현행과 기록에는 어느 절이 원본인지나 대신 볼 문서를 이어 적는다.

```markdown
# 알림 설계

> 상태: 일부만 현행. 3절과 5절만 지금 코드의 원본이고, 나머지 절은 지난 버전의 설계 기록이다. 지금 발송 규칙은 `docs/delivery.md`를 본다.
```

현행 문서는 지금 코드와 방향의 원본이고, 일부만 현행인 문서는 적어 둔 절만 원본으로 쓴다. 기록은 그때의 판단을 남긴 문서라서 지금 동작의 근거로 쓰지 않는다.

`scripts/gen-docs-index.mjs`가 문서마다 제목과 상태 줄을 읽어 `docs/README.md` 색인을 만든다. 색인 앞부분은 주제별 묶음으로, 주제마다 현행 문서를 먼저 적고 루트 문서와 다른 폴더의 문서를 그다음에, 기록과 보관 폴더의 문서를 뒤에 적는다. 뒷부분에는 상태별 목록을 둔다. 주제 목록은 스크립트 안의 표로 관리하고, 상태 줄이 없거나 어느 주제에도 들지 않은 문서가 있으면, 또는 주제 표가 없는 문서를 가리키면 스크립트가 색인을 만들지 않고 실패한다.

상태를 문서 안에 적으면 검색으로 문서 중간에 바로 들어온 사람과 AI도 맨 위만 보고 상태를 안다. 색인 파일 한 곳에서만 상태를 관리하면 고칠 곳은 하나로 줄지만 색인을 거치지 않고 문서를 연 쪽은 상태를 보지 못해서, 상태는 문서에 적고 색인은 그 줄에서 만들어 내도록 했다.

고치는 커밋에 따로 규칙이 걸린 문서와 다른 문서가 줄 번호로 인용하는 문서는 맨 위에 줄 하나를 끼워 넣으면 훅에 걸리거나 인용이 한 줄씩 밀려서, 상태를 문서에 적지 않고 스크립트 안의 표에 적는다. 이 문서들의 상태를 바꿀 때는 스크립트를 고친다.

상태 줄에 마지막으로 확인한 날짜를 넣으면 문서가 얼마나 오래됐는지 바로 알 수 있지만, 문서를 고칠 때마다 날짜도 고쳐야 하고 색인에 날짜가 들어가면 내용만 고친 커밋도 색인 검사에 걸린다. 언제 고쳤는지는 git 기록에 있어서 날짜는 넣지 않았다.

## 지난 문서와 낡은 절을 보관 폴더로 옮기는 방식

끝난 작업의 계획서와 점검 기록, 쓰지 않는 설계 초안은 `docs/_archive/`로 옮긴다. 파일은 `git mv`로 옮기고 내용은 글자 그대로 두며, 다른 문서로 가는 링크만 새 위치에 맞게 고친다. 지우고 git 기록에서 찾게 하면 폴더는 더 깔끔해지지만 그 문서를 경로로 가리키는 결정 기록을 읽을 때마다 커밋을 뒤져야 해서, 폴더만 옮겨 같은 파일 이름으로 바로 찾을 수 있게 했다.

ADR과 작업 기록은 쓴 뒤에 고치지 않는 문서라 옮기기 전 경로를 그대로 적고 있다. 그래서 보관 폴더의 README에 그 경로에 파일이 없으면 보관 폴더에서 같은 이름으로 찾으라고 적어 두었다. 현행 문서나 코드 주석이 근거로 가리키는 기록은 옮기지 않고 상태만 기록으로 적는다.

문서 하나가 통째로 끝나지 않고 일부 절만 낡았을 때도 같은 방식으로 옮긴다. 낡은 절은 보관 문서로 글자 그대로 옮기고, 원래 자리에는 절 번호와 제목을 그대로 둔 채 옮긴 곳을 가리키는 한 줄만 남긴다.

```markdown
## 3. 단계 체계

이 절은 [보관 문서](_archive/notification-v1-stages.md)로 옮겼다. 지난 버전의 단계 기록이고, 지금은 5절이 대신한다.
```

절 번호와 제목을 남겨 두면 다른 문서가 3절이나 절 이름으로 가리킨 곳을 그대로 찾을 수 있고, 남은 절의 번호도 바뀌지 않는다. 절 전체가 아니라 지금 코드와 맞지 않는 문장 몇 줄만 있으면 그 문장을 모은 보관 문서를 하나 만들어 원문 그대로 옮기고, 원래 자리에는 지금 사실을 적는다. 보관 문서에도 맨 위에 상태 줄을 두고 어느 문서에서 옮겼는지와 지금의 원본이 어디인지를 적는다.

## 기능 색인

기능이 어느 파일에 있는지는 루트의 `features.md` 한 문서에 모은다. 기능 하나가 한 항목이고, 항목마다 동작 요약과 설계 원본, 진입 함수, 읽고 쓰는 DB 표, 테스트 파일을 적는다.

```markdown
### 주문 접수

- 동작: 들어온 주문을 저장하고, 같은 손님이 잇달아 넣은 주문을 하나로 묶어 결제 단계로 넘긴다.
- 설계: `docs/orders.md` 2절 「주문 묶기」
- 진입: `src/orders.ts`의 `receiveOrder`, `mergePending`
- 표: `orders`, `order_items`
- 테스트: `test/order-merge.test.ts`
```

동작 요약은 한두 문장으로만 적고, 정한 값과 그 까닭은 설계 원본에서 읽는다. 진입 함수는 줄 번호 없이 파일 경로와 함수 이름으로 적는다. 프로젝트 CLAUDE.md에는 기능을 고치거나 찾기 전에 이 색인을 먼저 보라는 규칙을 두었다.

변경 기록과 기능 색인은 읽는 목적이 달라서 따로 두었다. 변경 기록은 언제 무엇이 바뀌었는지를 시간순으로 읽고, 기능 색인은 지금 무엇이 어디 있는지를 기능 이름으로 찾는다. 한 문서로 합치면 둘 다 찾기 어려워지므로, 변경 기록에는 머지 전에 한 줄 붙이는 규칙을 그대로 두고 기능을 찾을 때 여는 첫 문서만 기능 색인으로 바꿨다. [design-build-skills.md](design-build-skills.md)의 문서 표에 있는 features 문서가 지금 되는 기능을 소개하는 카탈로그라면, 이 색인은 기능에서 설계 원본과 코드로 가는 경로만 적는다.

## 커밋 훅이 검사하는 것

| 검사 | 스크립트 | 실패하는 경우 |
| --- | --- | --- |
| 문서 색인 | `gen-docs-index.mjs --check` | 상태 줄이 없는 문서가 있거나, 다시 만든 색인이 커밋된 색인과 다르거나, 주제에 들지 않은 문서가 있을 때 |
| 문서의 코드 경로 | `check-doc-refs.mjs` | 루트와 `docs/` 문서가 백틱 안에 적은 `src/`·`test/`·`scripts/` 경로가 작업 트리에 없을 때 |
| 기능 색인 | `check-features.mjs` | 색인의 경로가 없거나, 진입 줄의 함수 이름이 그 파일에 없거나, 표 줄의 이름이 스키마 파일에 없을 때 |
| 표 문서 | 테스트 | 스키마에 있는 표 이름이 표와 컬럼을 설명하는 문서에 한 번도 나오지 않을 때 |

세 스크립트는 `.githooks/pre-commit`에서 차례로 돌고, 기능 색인 검사와 표 문서 검사는 테스트로도 돈다.

보관 폴더처럼 이름이 밑줄로 시작하는 폴더와 ADR은 그때의 경로를 그대로 남기는 문서라서 코드 경로 검사에서 뺐다. 별표나 중괄호가 든 경로는 파일 하나를 가리키지 않아 건너뛰고, 없어진 파일을 문서에 남겨야 하면 백틱을 풀고 없어진 파일이라고 적는다.

기능 색인 검사는 진입 함수 이름을 그 경로의 파일뿐 아니라 파일과 같은 이름의 폴더 아래에서도 찾는다. 큰 파일을 같은 이름의 폴더로 나누고 원래 파일은 다시 내보내기만 하게 바꿔도 색인을 고칠 필요가 없도록 했다.

[system-map.md](system-map.md) §3의 기준으로 나누면, 문서를 읽기 전에 색인과 기능 색인을 먼저 보라는 규칙은 상황마다 판단이 필요해서 프로젝트 CLAUDE.md 문장으로 두었다. 경로와 이름이 실제로 있는지처럼 기계로 판정할 수 있는 일은 커밋 훅으로 내렸다.

## 한계

지금 장치는 문서가 없는 파일을 가리키거나 색인이 상태 줄과 달라지는 것처럼 기계로 판정할 수 있는 낡음을 커밋할 때 잡는 데 맞춰 두었다. 그 밖의 낡음은 사람과 AI가 읽어서 확인한다.

- 상태 줄 자체가 맞는지는 검사하지 않는다. 현행이라고 적은 문서가 코드와 달라져도 색인에는 현행으로 남아서, 코드를 바꾸는 커밋에서 그 기능의 설계 원본도 같이 고치는 규칙에 기댄다.
- 코드 경로 검사는 백틱 안의 경로만 보고, 백틱 없이 적은 경로와 줄 번호 참조, 문서 내용이 실제 동작과 같은지는 보지 않는다. 새로 적는 참조는 줄 번호 대신 파일 경로와 함수 이름으로 적어 검사 범위에 들어오게 한다.
- 기능 색인 검사는 적어 둔 항목이 낡았는지만 본다. 새 기능을 만들고 색인에 항목을 더하지 않아도 검사를 통과하므로, 함수 이름을 바꾸거나 기능을 더하면 같은 커밋에서 색인을 고친다는 규칙을 색인 문서 맨 앞에 적어 두었다.
- 커밋 훅은 repo를 새로 받을 때마다 `git config core.hooksPath .githooks`를 한 번 실행해야 켜진다.

## 일반화

- 문서가 많아지면 읽기 전에 근거로 써도 되는지를 문서 맨 위 한 줄로 알린다. 색인은 그 줄에서 만들어서 두 곳에 적힌 상태가 달라지지 않게 한다.
- 지난 내용은 지우지 않고 보관 폴더로 글자 그대로 옮긴다. 원래 자리에 절 제목과 옮긴 곳을 남기면 번호와 이름으로 적은 참조를 그대로 쓸 수 있다.
- 경로와 함수 이름, 표 이름처럼 코드와 함께 바뀌는 사실은 사람이 주기적으로 점검하지 않고 커밋마다 검사한다. 한 번 손으로 맞춰도 며칠 뒤면 없는 경로가 다시 생긴다.
- 기능을 찾는 문서와 변경을 기록하는 문서는 읽는 목적이 달라서 나눈다.

## 메타

이 글을 메타 repo에 둔 것은 다루는 문제가 특정 프로젝트의 설계 내용보다 문서가 늘어난 뒤 AI와 사람이 어느 문서를 근거로 쓸지 정하는 방법에 가깝기 때문이다. 문서 종류마다 역할과 owner를 정한 표는 [design-build-skills.md](design-build-skills.md)에 있고, 이 글은 그 표의 문서가 수십 개로 늘어난 뒤 문서마다 지금도 원본인지를 어떻게 알리고 검사하는지를 다룬다.

적용은 2026-11-24 random-ai-companion에서 했다. 그날 상태 줄과 문서 색인, 보관 폴더, 코드 경로 검사를 넣고 기능 색인과 그 검사를 더했으며, 다음 날 주제별 문서마다 낡은 절을 보관 문서로 옮기고 색인에 주제별 묶음을 더했다. 지금 색인에는 `docs/` 바로 아래 문서 32개와 보관 문서 39개가 있고, 기능 색인에는 항목 44개가 있다.
