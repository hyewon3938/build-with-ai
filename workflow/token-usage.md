# 토큰 사용량 측정과 줄이는 방법

> Claude Code의 토큰 사용량은 지시 파일이 얼마나 긴지보다, 세션 하나가 모델을 몇 번 부르는지와 캐시가 몇 번 끊기는지에 따라 크게 달라진다. 그래서 세션마다 호출 수와 캐시 끊김을 숫자로 남기는 것부터 시작했고, 낭비가 가장 컸던 곳부터 작업 방식을 고쳤다. 판단에 쓰는 모델과 검증 단계는 결과물의 품질과 바로 이어지는 부분이라 그대로 두었다.

## 사용량을 세는 방법

Claude Code는 세션마다 대화 기록을 jsonl 파일로 남기고, 모델을 부른 줄마다 새로 넣은 입력, 캐시에 새로 쓴 양, 캐시에서 다시 읽은 양, 출력 토큰 수를 적는다. 서브에이전트의 기록은 그 세션 폴더 아래 `subagents/`에 따로 쌓인다. `plugin/scripts/session-usage.mjs`는 이 기록에서 숫자와 도구 이름만 뽑아 세션 하나를 요약하고, 대화 본문은 출력하지 않는다.

```bash
node plugin/scripts/session-usage.mjs                 # 현재 폴더의 가장 최근 세션
node plugin/scripts/session-usage.mjs --since 7       # 최근 7일의 모든 세션을 한 줄씩, 끝에 도구·MCP·모델 합계
node plugin/scripts/session-usage.mjs --log ~/.claude/usage-log.tsv --label <세션 이름>
```

세션 요약에는 모델과 effort, 걸린 시간, compact 횟수, 호출 수, 매 호출이 다시 읽은 앞부분 크기, 서브에이전트별 사용량, 도구별 호출 수와 결과 글자 수가 나온다. 앞부분은 시스템 프롬프트, 도구 정의, 지시 파일처럼 첫 호출부터 계속 같은 내용을 말한다.

여러 세션을 비교할 때는 토큰 종류마다 무게를 다르게 매긴 합계를 쓴다. API 가격 비율을 빌려 새 입력 1, 캐시 쓰기 2, 캐시 읽기 0.1, 출력 5로 매겼다. 구독 플랜의 사용량 한도가 같은 비율로 세는지는 공개되어 있지 않아서, 이 합계는 세션끼리 비교하는 데만 쓰고 한도가 얼마나 남았는지 계산하는 데는 쓰지 않는다.

### 캐시 끊김 판정

캐시는 앞 호출까지 보낸 내용을 다음 호출이 그대로 다시 읽을 때만 싸게 쓸 수 있다. 앞 호출까지 캐시에 있던 양보다 다음 호출의 캐시 읽기가 90% 아래로 떨어지고 새로 쓴 양이 20K 토큰을 넘으면, 스크립트는 그 호출을 캐시가 끊겨 뒷부분을 다시 쓴 호출로 센다. 끊긴 호출마다 이유를 두 가지로 나눠 센다.

- 앞 호출과 60분 넘게 떨어진 호출. 캐시 보관 시간이 지나 처음부터 다시 쓴다.
- 앞 호출과 사이에 compact가 있었던 호출. compact는 앞 대화를 요약으로 바꾸기 때문에 앞부분만 남고 나머지를 전부 다시 쓴다.

어느 쪽에도 들지 않는 끊김은 스크립트가 끊긴 뒤 남은 캐시 길이별로 횟수를 세어 보여 준다. 같은 길이에서 여러 번 끊기면 그 길이 바로 뒤에 매 호출마다 바뀌는 내용이 들어 있다는 뜻이라, 그 위치를 보고 원인을 찾는다.

### 세션별 사용량 기록

`/build` 스킬의 마무리 절차에 이 스크립트를 돌려 세션 한 줄을 `~/.claude/usage-log.tsv`에 덧붙이는 단계를 넣었다. 한 줄에는 날짜, 세션, 모델, effort, 걸린 시간, 호출 수, 앞부분 크기, 캐시 끊김 횟수, 서브에이전트 수, 가중 합계가 들어가고, 세션 시작과 끝의 플랜 사용량 표시를 함께 적을 수 있다. 같은 종류의 세션을 설정만 바꿔 돌려 보면 이 파일에서 바로 비교할 수 있다.

## 7일 기록에서 찾은 낭비 지점

한 프로젝트에서 7일 동안 돈 세션을 모두 세어 보니, 가중 합계의 64%가 세션 하나에서 나왔다. 대기열을 이어서 돌리고 배포까지 확인하는 지휘 세션이었고, 5일 동안 한 세션으로 계속 돌았다.

- 이 세션은 compact를 443번 했다. 캐시가 끊긴 455번 가운데 441번이 compact 직후였고, 60분 넘게 쉰 뒤에 끊긴 것은 12번이었다. compact를 하면 앞부분 약 43K만 남고 나머지를 다시 써서, 대화가 길어질수록 compact 한 번에 다시 쓰는 양도 늘었다.
- 이 세션이 띄운 서브에이전트 195개 가운데 구현을 맡은 worker가 세션 사용량의 60% 정도를 썼다. 혼자 모델을 250~550번 부른 worker도 몇 개 있었다.
- 바꿀 값과 위치가 정해진 구현은 sonnet worker에 맡긴다는 기준이 있었지만, worker 28개 가운데 27개가 opus로 돌았다. worker는 부른 세션의 모델을 따라가서, 호출할 때 sonnet을 넘기지 않으면 기준이 적용되지 않았다.
- 같은 세션이 적대적 검증을 맡긴 verifier는 약 100개였고, 이들이 쓴 양은 7일 전체 사용량의 7% 정도였다.
- 로그와 목록을 통째로 출력한 명령이 쌓여서, 지휘 세션 본체가 받은 Bash 결과만 1천만 자 가까이 됐다.

다른 세션은 앞부분이 크거나 compact가 잦은 것이 문제였다.

- 매일 새벽에 도는 정리 작업은 첫 호출의 앞부분이 이미 150K를 넘었다. 지시서 하나가 7만 자가 넘고, 작업 첫 단계에서 읽는 데이터도 9만 자 가까이 됐다. 12분 동안 compact를 5번 하고, 할 때마다 350K 정도를 다시 썼다.
- 이슈 하나를 구현하는 일반 세션은 앞부분이 약 98K였고, 캐시 읽기의 68~80%가 앞부분 크기에 호출 수를 곱한 양이었다. 앞부분 가운데 지시 파일은 13K 정도이고, 도구 정의가 50K 정도로 가장 컸다.
- 한 번도 쓰지 않은 MCP 서버의 도구 정의도 매 호출 앞부분에 함께 들어갔다.

## 줄이는 방법

### 유지하는 설정

- 기본 작업 모델은 opus로 둔다. sonnet은 토큰당 값이 싸고 응답도 빠르지만, 구현하면서 판단할 것이 있는 일을 맡기면 다시 고치는 호출이 늘어 결과적으로 더 쓸 수 있다.
- verifier 검증은 그대로 둔다. 7일 사용량의 7% 정도라 비중이 작고, 보안·비가역 작업과 최종 보고의 핵심 주장에서 빠뜨린 것을 잡아 온 단계다. 일상적인 결론은 지휘 세션이 스스로 확인한다는 기존 기준도 그대로다.
- 보안 가드 훅과 커밋 훅은 토큰과 관계없이 안전을 지키는 장치라 끄지 않는다.

### 바꾼 설정

- 전역 지시 파일에서 사고 경위와 함정의 상세 절차를 별도 파일로 옮기고, 지시 파일에는 함정마다 한 줄과 상세 파일 위치만 남겼다. 같은 종류의 작업을 하기 전에 해당 절만 읽는다.
- 메모리 색인은 메모 하나에 한 줄인 형식을 유지하면서 줄마다 길게 붙어 있던 설명을 짧게 줄였다. 색인 줄은 회수할 메모를 고르는 데 쓰여서, 줄 자체는 지우지 않았다.
- 답이 끝날 때마다 다음 프롬프트를 제안하는 기능을 껐다. 이 기능은 답마다 모델을 한 번 더 부른다.
- 한 번도 쓰지 않은 MCP 서버와 브라우저 도구는 앱 설정에서 꺼서, 매 호출 앞부분에서 그 도구 정의를 뺀다.
- 세션마다 사용량을 TSV에 남겨, 설정을 바꾼 효과를 추정 대신 실제 숫자로 비교한다.
- sonnet은 판단 없이 끝낼 수 있는 기계적 작업에만 쓴다. 정해진 패턴으로 파일을 훑어 모으는 스캔, 바꿀 값과 위치를 지시서에 그대로 적어 준 편집, 정해진 명령을 돌려 결과만 정리하는 일이 대상이다. 오케스트레이션 규칙과 worker 설명에 호출할 때 sonnet을 직접 넘기라고 적어서, 기준이 부르는 쪽의 기억에 기대지 않게 했다.

### 다음 확인 항목

- 오래 도는 지휘 세션을 작업 단위로 끊는다. compact 직후 캐시 끊김이 가장 큰 낭비였고, 대기열 한 묶음이 끝날 때마다 새 세션을 열면 compact 횟수와 다시 쓰는 양이 같이 줄어든다.
- 구현 세션 하나를 effort medium으로 돌려, high로 돌린 같은 종류의 세션과 호출 수를 비교한다. effort를 낮추면 탐색과 자기 확인 호출이 줄어들 것으로 예상하지만, 아직 측정한 세션이 없다.
- 오래 도는 worker는 맡긴 범위가 넓었는지 지시서를 다시 본다. 한 worker가 수백 번 부르는 일이 반복되면 작업을 더 잘게 나눈다.
- 새벽 정리 지시서와 첫 단계에서 읽는 데이터를 필요한 부분만 읽도록 나눈다.
- 큰 출력을 내는 명령은 결과를 파일로 저장하고 필요한 줄만 읽는다.

## 제외한 방법

- 모든 세션을 sonnet으로 바꾸지 않는다. 설계와 판단이 들어가는 세션에서는 다시 고치는 비용이 아끼는 양보다 크다.
- verifier를 줄이거나 없애지 않는다. 차지하는 비중은 작은데, 놓친 것이 생기면 되돌리는 비용이 크다.
- 메모리 색인을 통째로 지우지 않는다. 색인이 없으면 필요한 메모를 찾지 못한다.
- 지시 파일은 앞부분의 13% 정도라 더 줄여도 전체에서 3% 안팎이어서, 지시 파일을 더 줄이는 일에는 집중하지 않는다.
