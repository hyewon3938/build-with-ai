# 스킬 실측 감사 — 산출물이 말해주는 워크플로우의 구멍 (2026-07)

> 스킬 문서를 다시 읽으며 점검한 게 아니라, 스킬이 만들겠다고 약속한 산출물이 실제로 존재하는지를 대조했다. 문서 리뷰였으면 못 봤을 구멍 3개가 나왔다.

## 왜 했나

`/init-project` → `/design` → `/build` 스킬 체계를 몇 달째 운영하면서 마스터 이슈 10여 개가 이 파이프라인을 통과했다. 충분한 표본이 쌓였으니 "잘 만들어서 잘 쓰고 있는 건지"를 점검할 시점 — 그런데 점검 방식이 문제였다. 스킬 본문을 다시 읽는 건 자기 문서를 자기 눈으로 재확인하는 일이라, 그럴듯하게 읽히면 통과된다.

그래서 방향을 뒤집었다. **스킬이 약속한 산출물의 현재 상태를 실측하고, 약속과 실측의 차이에서 역으로 스킬의 결함을 찾는다.**

## 점검 방식

- 스킬 본문 3종 + 보조 파일(references/templates)은 지휘 세션이 직접 정독 — 판단 품질이 걸린 부분은 위임하지 않는다
- 산출물 실측은 정찰 에이전트 2개에 병렬 위임: 계획서 디렉터리, design-notebook, ADR 인덱스, features.md, project-history, 최근 머지 PR 6개의 구조를 파일 날짜·이슈 상태와 대조
- 발견 → 개선 적용 → 문서 동기화 → 검증의 나머지 단계도 역할별 에이전트로 분산 (기계적 갱신은 하위 모델, 판단·종합은 상위 모델)

## 실측 결과 ① — 약속대로 살아 있던 것

| 산출물 | 실측 |
|------|------|
| design-notebook | 감사 시점 마스터 파일 9개. Phase 섹션 5종 하위구조(결정 요약·분기점·포기한 안·미해결·회고)가 최근 마스터들에서 온전히 유지 — 단 초기·미완결 마스터 일부는 회고 헤더가 비어 있음 (아래 "검증의 검증" 참조) |
| ADR | 60개 연번 gap 없음, README 인덱스가 최신 번호까지 정확 |
| PR 본문 | 최근 코드 변경 PR 5/5가 "코드 리뷰 결과 + 테스트" 섹션 보유 |
| 도메인 문서 | owner 2단계 분리(설계=골격, 구현=본문) 도입 이후 누락 재발 없음 |

공통점이 뚜렷했다. **살아 있는 산출물엔 전부 스킬 안에 번호 달린 실행 단계와 강제 장치가 있었다** — TODO 마커를 grep으로 점검하게 하거나, "파일을 읽지 않고 체크리스트만 쓰는 건 리뷰가 아니다"처럼 회피 경로를 막아둔 것들.

## 실측 결과 ② — 구멍 3개

### 1. project-history 5주+ 정체

마일스톤급 완료 기록이 5주 넘게 갱신 0건. 그 사이 close된 마스터급 작업 여러 개가 통째로 누락됐다. 단계 자체는 스킬에 있었다("마일스톤급일 때만 갱신"). 문제는 **그 단계가 PR 생성 직후에 있다는 것** — 세션이 PR을 만들고 자연스럽게 끝나면, 머지 이후에 일어나야 할 판단은 아무 데도 걸려 있지 않다.

### 2. 계획서 "휘발" 정책 미작동

계획서는 "휘발 문서 — 작업 끝나면 아카이브"로 선언돼 있었는데, 실측하니 이슈가 close된 계획서 50여 개가 라이브 디렉터리에 방치돼 있었다. 유일한 정리는 한 번의 수동 청소뿐. 원인은 명확했다. **"휘발"이라는 성질만 정의하고 행위자를 정의하지 않았다** — 아카이브를 누가, 언제 하는지가 어느 스킬의 실행 흐름에도 없었다.

### 3. features.md 갱신 단계의 비대칭

기능 카탈로그는 최근 작업 일부만 반영된 상태였고, 한 마스터의 기능군은 통째로 빠져 있었다. 스킬을 보니 이유가 보였다. **폐기 시 카탈로그에서 제거하는 단계는 있는데, 추가하는 단계가 없었다.** 제거 단계는 과거 사고(폐기 기능이 문서에 "운영 중"으로 남은 건)를 계기로 명문화됐지만, 추가는 "알아서 하겠지"로 남아 있었던 것.

세 구멍의 공통 원인은 하나로 수렴한다:

> **owner가 표에만 존재하는 문서는 갱신이 멈춘다.** "이 문서의 갱신 주체는 /build"라고 선언하는 것과, /build 실행 흐름에 번호 달린 단계가 있는 것은 완전히 다른 일이다.

## 개선 — 이전 vs 이후

### /design

| 이전 | 이후 |
|------|------|
| `model: opus` 고정 핀 | 핀 제거, 세션 모델 상속 — 모델 라인업이 바뀌면 핀은 상한이 아니라 하향이 된다. 무거운 설계는 상위 모델 세션에서 열라는 권장만 남김 |
| 마스터 cross-check 4항목 (원칙·ADR·포기한 안) | +1: 직전 phase의 project-history·features.md 기록 누락을 다음 진입 시점에 회수 — 스킬 밖에서 close된 작업의 안전망 |
| 인터뷰 규칙 한 줄 ("한번에 너무 많이 X") | 질문은 핵심·맥락 묶어 한 번에 / 옵션 라벨은 숫자·알파벳만 / **뼈대 결정은 개념·흐름 수준의 명시적 체크포인트로 확인** (디테일은 위임, 핵심은 사용자가 직접 검증) |
| 코드베이스 탐색 직접 수행 | 다수 파일 탐색은 scout 병렬 위임, 결론만 수신 — 설계 판단용 컨텍스트 보호 |
| — | 이슈·브랜치명 공개 텍스트 보안 규칙 / 새 세션 인계 시 휘발 컨텍스트만 전달(문서 본문 복제 금지) 명문화 |

### /build

| 이전 | 이후 |
|------|------|
| features.md 갱신 단계 없음 (제거만 존재) | 3-4단계 신설 — 신규 기능 시 카탈로그 추가, 폐기 정리와 대칭, 구현 커밋과 같이 |
| PR 생성이 사실상 종점 | PR 직후 `gh pr checks --watch` CI 확인 의무 + **10단계 "머지 후 마무리" 신설**: CI·배포 확인 → 프로덕션 검증 → 계획서 아카이브(+close된 잔존 계획서 일괄) → project-history 재점검 |
| 테스트 실행만 | 정적 검사(타입체크·린트) 선행 명시 |
| — | 독립 작업 단위 worker 병렬 위임 옵션 (지시서 4요소 필수) |

### /init-project

| 이전 | 이후 |
|------|------|
| 단일 커맨드 파일 (`~/.claude/commands/`) | 스킬 형식(`~/.claude/skills/init-project/SKILL.md`)으로 이전 — 3종 위치·형식 통일 |
| conventions·project-history·ADR만 생성 | **5문서 아키텍처 전체 부트스트랩**: features.md 골격, design-notebook/, domains/(해당 시), 비공개 문서 자리(+gitignore), plans/_archive — 후속 스킬이 전제하는 구조를 초기화가 실제로 만들어 줌 |
| 문서 세트 고정 | 규모 판단 신설: 실험·일회성 / 지속 개발 / 도메인 분리 3단계 — 오버엔지니어링 경계 |
| "각 단계 완료 후 확인" (12회) | 체크포인트 3개로 통합: 인터뷰 요약 / 생성 계획 일괄 승인 / 원격·비가역 작업 직전 |

### 구조 정리

- 프로젝트 저장소에 남아 있던 초기 버전 커맨드 사본(설계·구현·리뷰)을 제거하고 글로벌 스킬로 일원화 — 같은 이름이 두 곳에 등록되면 어느 쪽이 실행되는지부터가 모호해지고, 안 쓰는 쪽은 조용히 늙는다
- 방치돼 있던 close 이슈 계획서 51개를 일괄 아카이브 — 새 정책의 소급 적용

## 배운 것

1. **산출물 실측이 문서 리뷰보다 정직하다.** 스킬 본문만 읽었으면 세 구멍 모두 지나쳤다 — 본문은 그럴듯하게 읽힌다. 점검 질문은 "스킬이 잘 쓰여 있나"가 아니라 "스킬이 약속한 파일이 지금 그 상태인가"여야 한다.
2. **역할 선언과 실행 단계는 다르다.** 살아남은 산출물과 죽은 산출물을 가른 건 문서의 중요도가 아니라, 스킬 실행 흐름 안에 번호 달린 단계 + 강제 장치가 있는지였다.
3. **세션의 자연 종료 지점이 워크플로우의 실질 종점이 된다.** PR 생성에서 세션이 끝나면 머지 이후의 일은 일어나지 않는다. 종료 지점 뒤의 일은 명시 단계로 끌어와야 한다.
4. **누락은 발생을 막는 것보다 회수 경로를 만드는 게 견고하다.** 어떤 단계든 스킵될 수 있다 — 다음 진입 시점(cross-check)에서 직전 기록을 점검하는 회수 루프가 있으면 누락이 영구화되지 않는다.
5. **검증의 검증 — 실측 주장도 반증을 통과해야 한다.** 이 감사의 초고는 "마스터 파일 10개, 전 파일 완전 일관"이라고 썼다. 개선 적용 후 붙인 적대적 검증 에이전트가 헤더 단위 재실측으로 이걸 반증했다: 실제 9개, 하위구조 완전 보유는 파일별 6\~8/9. 스팟체크(최근 2개 파일) 결과를 전체로 일반화한 오류였다. 교훈 둘 — 표본 확인을 전수 주장으로 부풀리지 말 것, 그리고 공개 문서에 절대 수치를 박을 땐 "감사 시점 N개"처럼 시점을 고정할 것. 실측의 정직함을 말하는 문서일수록 자기 수치가 신뢰의 시금석이 된다.

## 메타

이 글이 이 repo에 있는 이유: 특정 프로젝트의 기능 이야기가 아니라 "스킬을 어떻게 유지보수하는가"의 방법론이라서. 스킬은 만들 때 완성되는 게 아니라, 산출물이 충분히 쌓인 뒤 실측으로 점검할 때 한 번 더 완성된다. 같은 방법(약속된 산출물 실측 → 공통 원인 추출 → owner를 실행 단계로 승격)은 어떤 워크플로우 자동화에도 적용된다.
