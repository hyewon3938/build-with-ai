# 버전마다 API 비용을 결산하는 틀

> LLM을 부르는 서비스의 API 비용은 버전 하나를 마칠 때마다 같은 방법으로 계산해야 버전끼리 비교할 수 있다. 그래서 호출마다 토큰을 남기는 운영 DB와 실제 금액이 든 콘솔 청구 CSV를 대조해 금액을 호출마다 나누는 결산 도구를 만들고, 리포트 목차와 버전 비교표를 고정해 두었다. 공개될 수 있는 문서에는 토큰, 비율, 공개 단가로 계산한 지수만 적고, 금액은 커밋하지 않는 파일에만 둔다.

## 버전 단위로 결산하는 이유

한 프로젝트에서 비용이 신경 쓰일 때마다 그때그때 숫자를 뽑아 보니, 측정할 때마다 기간을 자르는 기준과 단가와 분모가 달라서 앞 측정과 비교할 수 없었다. 버전 하나가 끝나는 시점은 기능 변화가 한 번 정리되고 다음 방향을 정하기 직전이라, 이때 같은 틀로 결산해 두면 이번 버전에서 무엇이 비용을 바꿨는지와 다음 버전에서 무엇을 먼저 줄일지를 함께 정할 수 있다.

결산은 같은 지표를 같은 순서로 남기는 데 목적을 둔다. 리포트 목차는 템플릿 하나로 고정하고, 버전마다 한 줄씩 더하는 비교표를 따로 두어서 다음 버전 결산이 끝나면 표 한 줄만 보고도 앞 버전과 비교할 수 있게 했다.

## 자료 두 가지와 대조

결산에 쓰는 자료는 두 가지다.

- **운영 DB의 호출 기록.** 서비스가 모델을 부를 때마다 용도, 캐릭터, 모델, 새 입력, 캐시 쓰기, 캐시 읽기, 출력 토큰을 한 행에 남긴다. 무엇에 썼는지는 알 수 있지만 금액은 없다.
- **콘솔 청구 CSV.** 날짜, 모델, 토큰 종류, API 키마다 실제 청구 금액이 있다. 금액은 정확하지만 어느 기능이 썼는지는 알 수 없다.

결산 도구는 모델과 토큰 종류마다 CSV 금액을 DB 토큰 합으로 나눠 실효 단가를 구하고, 호출마다 그 단가를 곱해 금액을 나눈다. 그다음 용도, 캐릭터, 유저, 단계, 주차별로 다시 모은다. 실효 단가가 공개 단가와 3% 넘게 다르면 결산을 진행하기 전에 원인부터 찾는데, 지금까지는 DB에 남지 않은 호출, 기간 안의 단가 변경, 서로 다른 캐시 쓰기 요금이 한 칸에 합쳐진 경우가 원인이었다.

CSV에는 있는데 DB 토큰으로 나눌 수 없는 금액은 버리지 않고 날짜별로 따로 모아 둔다. 호출마다 나눈 금액, 웹 검색 요금, 나누지 못한 금액을 더한 값이 CSV 합계와 맞는지 도구가 확인하고, 맞지 않으면 차이를 결과에 그대로 적는다. 버전 사이 비교에는 단가 변화가 섞이지 않도록 모든 토큰을 같은 공개 단가로 다시 계산한 값을 쓰고, 앞 기간을 100으로 둔 지수로 적는다.

## 커밋하는 것과 커밋하지 않는 것

결산 문서는 repo에 커밋하지만 개인 비용 금액은 공개될 수 있는 곳에 남기지 않는다. 그래서 같은 도구로 결과를 두 번 뽑는다.

| 결과 | 담는 것 | 두는 곳 |
| --- | --- | --- |
| 커밋용 | 토큰, 건수, 비율, 공개 단가, 같은 단가로 계산한 지수 | `docs/cost/` |
| 로컬용 | 위 내용에 실제 금액과 금액 기준 비중을 더한 것 | 커밋하지 않는 `LOCAL-COST.md`와 `data/cost/` |

청구 CSV를 넣지 않고 돌리면 도구가 금액 키를 하나도 내지 않는다. 사람이 결과에서 금액을 지우는 방식은 한 번만 빠뜨려도 커밋에 들어가서, 금액이 처음부터 만들어지지 않게 했다. 테스트는 커밋용 결과와 HTML에 달러 표기와 유저 식별자가 없는지 확인하고, 결과에 든 문자열 값에 금액이 섞이면 도구가 결과를 내지 않고 멈춘다. 리포트 md도 같은 규칙을 따라서, 같은 절의 실제 금액은 로컬 파일의 같은 버전 절에 같은 순서로 적는다.

운영 DB를 내보내는 스크립트는 DB를 읽기 전용으로 열고 대화 본문과 프롬프트 본문은 내보내지 않는다. 토큰 수와 블록 이름, 해시만 있으면 결산에 충분하다.

## 리포트 틀

버전 리포트는 템플릿의 목차를 그대로 따른다.

1. 결론
2. 합계와 추이
3. 용도별 비중
4. 답장 1건, 유저 하루 같은 단위 비용
5. 비용이 바뀐 요인
6. 이번 버전 비용 작업의 효과
7. 줄일 방안과 품질 영향
8. 하지 말 것
9. 규모와 다음 버전 목표
10. 계측 보강
11. 방법과 한계, 앞 버전과 비교

줄일 방안에는 방안마다 품질에 주는 영향을 같이 적고, 품질을 건드리지 않는 방안과 품질을 걸고 고르는 방안을 나눠 둔다. 하지 말 것에는 비용은 줄지만 서비스가 지키려는 것을 해치는 방안을 근거와 함께 적어서, 다음 버전에서 같은 제안이 다시 나오지 않게 한다. 계측 보강에는 이번 결산에서 DB에 없어 어림해야 했던 값을 적고, 다음 버전이 시작되기 전에 기록하도록 고친다.

md 리포트는 결산마다 반드시 쓰고, HTML 시각화는 필요할 때만 결산 결과 JSON을 넣어 명령 하나로 만든다. 로컬용 결과를 넣으면 금액이 든 HTML이 나와서 커밋하지 않는 폴더에만 두고, 커밋용 결과를 넣으면 토큰과 비율로만 그린다.

## 결산 함정

아래는 첫 결산에서 실제로 걸렸거나 걸릴 뻔한 함정이고, 프로젝트의 결산 절차 문서에도 같은 목록을 두어 새로 걸린 것이 생기면 결산할 때 더한다.

- **날짜 기준.** 콘솔 청구는 UTC 날짜이고 DB 기록 시각은 서비스 시간대였다. 결산 기간은 콘솔에 맞춰 UTC로 자르고, 리포트 안의 시각만 서비스 시간대로 쓴다.
- **시각 문자열 형식.** DB가 날짜와 시각 사이를 빈칸으로 적는데, `T`가 든 값과 문자열로 비교하면 그날 행이 빠진다.
- **콘솔 값 지연.** 청구 값은 몇 시간 늦게 들어오고 월말 뒤 며칠 동안 바뀐다. CSV는 기간이 끝나고 일주일쯤 지난 뒤에 받는다.
- **API 청구 밖의 호출.** 구독으로 돌린 배치와 도구 호출은 DB에도 콘솔에도 없다. 청구가 없을 뿐 원가가 없는 것은 아니라서 리포트에 따로 한 줄 적는다.
- **로컬에서 돈 호출.** 로컬에서 API로 돌린 도구는 콘솔에는 있고 운영 DB에는 없어서, 실효 단가가 공개 단가보다 높게 나왔다. 로컬용 API 키를 따로 쓰면 CSV의 API 키 칸으로 나눌 수 있다.
- **캐시 쓰기 요금 두 가지.** 1시간 캐시 쓰기와 5분 캐시 쓰기는 단가가 다른데 DB는 한 칸에 합쳐 적었다.
- **예전 문서의 단가.** 예전 측정 문서에 적힌 캐시 읽기 단가가 공개 단가의 두 배였다. 단가는 공개 자료에서 다시 확인하고 적용 시작일과 함께 파일 하나에 둔다.
- **출력 토큰과 생각 과정.** 출력 토큰에는 생각 과정이 들어가서, 저장된 답장 글자 수로 출력 비용을 어림하면 작게 나온다.
- **웹 검색 요금.** 검색은 요청마다 따로 요금이 붙는데 DB에는 요청 수가 없어 검색어 수로 어림해야 했다. 결산 뒤 요청 수를 DB에 남기도록 고쳤다.
- **유저 단위 집계.** 유저가 중간에 캐릭터를 바꾸면 캐릭터 단위로 묶은 비용이 유저를 둘로 나눈다. 유저 단위로 볼 때는 유저 키로 묶는다.
- **배포가 만든 캐시 쓰기.** 프롬프트 앞부분의 규칙 블록을 고쳐 배포하면 첫 호출이 그 블록과 뒤에 놓인 블록을 모두 다시 쓴다. 배포가 잦은 버전은 이 몫이 커서, 배포를 하루 1~2번으로 묶었고 그 뒤 답장당 캐시 쓰기가 줄었다. 같은 날 다른 캐시 작업도 들어가서 두 작업의 효과는 나눠 재지 못했다.
- **기간 끝의 단위 비용.** 테스트가 끝나 가는 주는 대화가 줄어 식은 캐시를 다시 쓰는 일이 늘고, 답장 1건 비용이 올라간다. 주차끼리 비교할 때는 답장 건수를 같이 본다.

## AI와 결산할 때

결산을 시작하기 전에 필요한 자료, 최종 리포트에 나와야 할 값, 커밋할 것과 로컬에 둘 것을 먼저 정했다. 이 세 가지가 정해져야 서브에이전트에 나눠 맡긴 분석이 같은 분모와 같은 기간으로 돌아오고, 결과를 합칠 때 다시 맞추는 일이 줄어든다.

분석마다 같은 값이 다르게 나온 곳은 결산 도구로 다시 계산해 어느 쪽을 택했는지 리포트의 방법과 한계 절에 적었다. 리포트가 길고 분석이 여러 갈래라 세션 압축으로 중간 결론을 잃기 쉬워서, 결론은 대화에 두지 않고 결과 JSON과 리포트 파일에 바로 적었다.

결산 절차와 함정 목록, 리포트 템플릿, 단가 파일, 버전 비교표가 repo에 있어서 다음 버전 결산은 기간을 더하고 같은 명령을 돌리는 데서 시작한다.
